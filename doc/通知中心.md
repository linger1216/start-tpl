# 通知中心与调度

通知事件保存在 `sys_notification`，各接收人和渠道的投递状态保存在 `sys_notification_delivery`，外部投递的每次尝试保存在 `sys_notification_attempt`。站内通知也是一条 `in_app` 投递；列表和已读操作按当前用户及渠道限定。事件与所有投递在同一个事务内创建，业务需要原子提交时使用 `createNotification(tx, input)`。

服务商名称和每次尝试的错误保存在尝试记录中，供排查历史；投递记录的 `last_error` 保留当前错误摘要，还用于记录租约耗尽、最终结果未知等不属于一次完成尝试的情况。老库初始化时会删除投递表中重复的 `provider` 列；历史尝试记录不删除。

```ts
await sendNotification({
  type: "example.changed",
  source: { type: "example", id: objectId },
  title: "状态已更新",
  content: "请查看详情",
  dedupeKey: `example.changed:${eventId}`,
  recipients: [{ userId, channel: "in_app" }],
});
```

相同幂等键只创建一个事件；接收人和渠道的组合有唯一约束。站内投递入库即为 `sent`，`read_at` 只表示站内消息已读，与审批或征询动作的 `viewed_at` 独立。`title` 入库前按 `varchar(128)` 统一按码点截断（`NOTIFICATION_TITLE_MAX`）—— 调用点常把任务名前缀进标题，而任务名上限 255，不截断会让同事务的业务写一起回滚。SSE 是刷新信号而非存储：同进程发送立即通知浏览器，其他进程写入通过 25 秒刷新信号和现有轮询最终显示。

**SSE 事件分两种，失效范围不同**：`notice.new` 是真实业务事件，失效整个 `notice.*` **和** `taskClose.*`（「我的任务」红点也吃通知）；`notice.refresh` 只是跨进程兜底心跳，只失效 `notice.list` 与 `taskClose.menuBadge`。心跳每 25 秒一次，若让它全量失效 `taskClose.*`，任务页会跟着抖动。连接清理有三条路径：`request.signal` abort、`ReadableStream` 的 `cancel()`、写失败或心跳抛错时的即时 `unsubscribe`。注意 `start()` 的**返回值不会被调用**（规范只把它的 thenable 当 promise 用），所以清理函数必须挂在 `cancel()` 能碰到的外层作用域上，而不是 `return cleanup`。反代静默断链时是否触发 abort 依平台而定，`cancel()` 与写失败是兜底。

**投递管理接口的权限是失败关闭的**：`notice.history` / `notice.attempts` 读的是跨用户数据（收件人姓名、渠道状态、服务商错误原文），登记在 `PERM_BY_PATH` 的 `sys:notice:history` 下。权限体系未配置（`sys_casbin_rule` 一条策略都没有）时中间件会放行，这两个 resolver 内另有一道兜底 —— 那种情况下只有管理员/超管能读。

## Worker 与渠道

```bash
pnpm db:create
pnpm db:seed:menus
pnpm db:seed:rbac
pnpm dev       # Web
pnpm worker    # 另开一个终端
```

生产环境同时部署 Web 和 Worker 两个进程；`docker compose up -d` 包含独立 `worker` 服务。Worker 从数据库条件更新认领投递，租约到期后可由其他 Worker 恢复；失败按指数退避重试，最多五次，结果和错误写入投递及尝试表。每轮认领一小批（`delivery-runner.ts` 传 20；早先只取 1 条，导致吞吐被钉在 12 条/分钟）。外部服务调用在事务之外，因此语义是**至少一次**：进程在服务商已接收但结果未写回时退出，仍可能重发；Provider 应使用传入的 `idempotencyKey`。撤回 / 驳回时 `cancelPendingNotifications` 会同时取消 `pending` 和**租约已过期**的 `processing` —— 后者是 Worker 崩溃留下的，不取消会在租约到期后被另一个 Worker 重新认领并真的发出去。仍持活跃租约的在途调用不碰。

邮件默认复用 `src/lib/mailer.ts`，须配置 `MAIL_DRIVER=smtp` 和 `SMTP_*` / `MAIL_FROM`。默认 console 邮件驱动只适用于认证链接调试，不会被通知 Worker 当成真实投递。短信与邮件分别通过 `SMS_PROVIDER_MODULE`、`EMAIL_PROVIDER_MODULE` 指向自定义模块，该模块默认导出 `{ name, send }`；`send({ idempotencyKey, target, title, content })` 返回 `{ messageId? }`。开发时可设 `SMS_PROVIDER=console` 查看模拟内容，模拟不会被标记为发送成功。未配置服务商时会记录失败并重试，不会虚报已发送。模块路径需要在 Worker 容器内可访问。

## 调度管理

`sys_scheduled_job` 保存计划、启停状态、下次执行时间和租约，`sys_job_execution` 保存执行历史。Worker 使用数据库条件更新认领，注册的处理器通过子进程执行；超时会终止子进程，过期租约可恢复。处理器需自行保证重试幂等。`/settings/scheduler` 提供启停、立即安排、间隔或 Cron 和时区配置、最近执行记录；写操作需要 `sys:scheduler:manage`。Cron 只用于计算下次时间，不依赖进程内定时器持有任务状态。

## 任务闭环

任务创建或编辑时可分别设置执行人的截止提醒、节点处理人的未查看提醒：每组最多 10 个不重复时间点，共用所选站内、短信、邮件渠道；执行人可选择截止时，节点必须在激活后。节点默认激活后 60、180 分钟站内提醒，执行人默认关闭。截止时间为空或尚未分配执行人时保留配置但不安排执行人提醒；配置修改只安排未来时间点。

新任务在 `tc_task.reminder_config` 保存配置，在 `tc_task_reminder` 持久化计划。Worker 每分钟扫描，锁任务与计划行并重新检查任务、处理人与节点资格，同事务创建通知并完成计划；进程暂停期间已安排的提醒恢复后仍会执行。旧任务未保存配置时继续沿用 60、180 分钟站内提醒，历史 `action.unviewed` 幂等键继续生效。节点已查看、结束、任务删除或进入结束状态及配置变化会取消不再适用的计划；外部投递已进入服务商调用的仍按通知中心租约规则处理。

任务创建者、执行人、参与人或管理员可在参与人行向对应人员发送提醒，并选择一个或多个渠道；接口也支持一次处理多个收件人。同一任务同一收件人冷却 30 分钟，冷却人员跳过，其余人员继续；请求 ID 提供幂等。没有有效联系方式的渠道记为失败，其他渠道继续；任务提醒历史隐藏联系方式，普通参与人看到通用投递错误，管理员可看详细错误。旧动作催办记录仍保留。用户编辑页可配置联系电话。

## 数据库初始化

MySQL 使用 `pnpm db:create`；达梦使用 `pnpm db:dm:create-ba`，两套脚本包含通知、调度及任务闭环表。开发阶段直接废弃旧通知表，不迁移旧消息。

建表脚本不 drop 表。老库里遗留的 `sys_notice` 需手工清理一次：

```sql
-- MySQL:确认行数后删除,旧消息不迁移
select count(*) from sys_notice;
drop table sys_notice;
-- 达梦:drop table "SYS_NOTICE";
```

达梦 DDL 和并发行为应在目标版本实库验证，不能以 MySQL 结果代替。
