# 任务闭环

任务闭环是模板驱动的通用协作能力，不绑定具体业务。任务流程快照、审批和征询、独立填报、自由回复分别承担不同职责；通知与调度是独立模块。填报设计见 [task-forms.md](task-forms.md)，通知与 Worker 见 [通知中心.md](通知中心.md)。

## 代码与存储

- `src/integrations/trpc/routers/task-close.ts`：组合入口；`task-query.ts`、`task-record.ts`、`task-member.ts`、`task-action.ts`、`task-comment.ts`、`task-workflow.ts`、`task-report.ts` 按职责实现接口，`task-shared.ts` 保存共用的授权与事务逻辑。
- `src/lib/task-close-spec.ts` / `task-close-log.ts`：流程状态与活动日志的客户端安全词表。
- `src/lib/task-report-spec.ts` / `task-report-summary.ts` / `task-report-excel.ts`：填报校验、汇总和受限 Excel 处理。
- `src/components/modules/task-close/`：任务列表、详情、流程模板、填报模板与填报界面。
- `src/db/data-base-schema.ts`、`scripts/create-system-tables.ts`、`scripts/create-better-auth-tables-dm.ts`：模型及 MySQL、达梦初始化；`scripts/sync-table-meta.ts` 是表列注释唯一真源。

| 表 | 职责 |
| --- | --- |
| `tc_workflow` | 可编辑的任务流程模板，`payload` 定义状态与转移 |
| `tc_task` | 任务、创建人、说明内容及创建时固定的流程快照;`parent_id` / `report` 承载父子填报与数据规则 |
| `tc_content_revision` | 说明 / 链接 / 附件的内部修订快照（**界面已不出入口**；留着是给旧附件保留归属） |
| `tc_member` | 参与者与执行人关系；一个任务至多一个有效执行人 |
| `tc_action` | 审批和征询的当前处理节点，通过 `root_action_id`、父节点和顺序组织 |
| `tc_comment` | 自由文字、附件与结构化 @，不作为正式填报 |
| `tc_log` | 与业务同事务、只增不改的活动历史 |
| `tc_report_template` | 填报模板(单版本,`payload` 即当前结构;`shared` 控制可见性) |
| `tc_task_report` / `tc_report_submission` | 每个任务各有一份填报草稿;`tc_report_submission` 为历史快照,当前流程不再写入 |

## 任务与权限

`tc_member` 是执行人的唯一权威来源；新增或转交时锁定任务行，防止并发产生多个执行人。
**建任务时选多个执行人 = fan-out**:事务内建 1 条**父任务**(`parent_id = null`,不设执行人,承载母版数据)
+ N 条**子任务**(`parent_id = 父`,`tc_member` 里各挂一名执行人,`tc_task.report` 里带各自的过滤规则)。
**说明 / 链接 / 附件在 fan-out 时复制给子任务**;其中**说明**是"整件事"的描述 —— 父任务之后改说明,
会同步写到全部子任务(链接 / 附件不走同步,详情页按整棵树取并集显示)。单执行人则是普通一条任务。数据范围挂在**成员**上(`members[].filter`,一条等值条件),缺省沿用任务级数据规则
(`report.filter`);不配就是全部数据。**下发即复制**:子任务的填报是父任务母版行的独立副本,父子各存各的、互不加锁;
子任务里点「保存」才把这份副本同步回父任务(接口 `reportSyncToParent`,只对子任务开放)。界面里「带数下发」是一个「数据」小字:展开后先导入 Excel(单行中文表头,
空模版表头即可),再逐人配数据范围,多执行人必须配置互斥范围。

任务卡片顶行左格是**发件抬头**:执行人圆牌 + 姓名(「发给谁」,`taskList.items.executorName` / `taskGet.children[].executorName` 由 `executorNamesOf` 从 `tc_member` 派生 —— fan-out 子任务创建人全都一样,只看 `creator_id` 分不出发给谁);fan-out 的父任务是分派容器、没有唯一收件人,退回类型图标块。

「我的任务」只列顶层任务(父任务卡片带「N 个子任务」);**我在某条子任务里有角色(执行人或参与者)时,那条子任务也直接列出来** —— 参与的人要能看到自己的活。**任务详情只对相关方开放**(创建人 / 参与者 / 执行人 / 管理员;再加「父任务的参与者能看子任务」这条向下可见):不是相关方就算直接访问 URL 也拿不到数据,前端提示「权限不足」后跳回「我的任务」。**点卡片一律进任务详情**,不再单开「子任务卡片页」——
父任务详情左画布顶部用**同一张任务卡片**列出它的子任务(卡上有状态章、优先级、执行人与截止,也可以再点进去看那条子任务的详情)。
**子任务看不到父任务详情**(没有「返回父任务」入口)。

父子之间的数据分三种口径,别混：

| 内容 | 父子关系 |
| --- | --- |
| 填报数据 | 下发时复制；每个任务独立保存和检查 revision。子任务手动同步时，用自己的行替换父任务中属于该子任务范围的行 |
| 链接 / 附件 / 说明 | 创建时复制；详情读取整棵树的链接与附件并集，编辑使用当前任务自己的内容 |
| 评论 / 动态 / 成员 | 按任务分别保存 |

多个执行人的筛选范围必须两两互斥，包括未配置筛选的全量范围。同步是按范围整片替换：父任务在下发后对同一范围的修改可能被子任务覆盖；已有任务的历史范围也可能重叠，操作前需核对。删除父任务会连带软删子任务。

附件写入走 `taskAttach`(**任务相关方都能加**,只合并 `payload.attachments`,
从库里取旧值再拼,不会覆盖链接 / 说明);`taskGet` 另外下发 `own`(本任务自己的内容),编辑与附件弹窗回存用它,
免得把兄弟任务的内容克隆一份。
**例外**:把子任务交给我的(我是它的执行人),
列表里直接给我一条 —— 否则执行人没有入口干活。转交会在同一事务中变更成员关系并记录历史。创建任务可以暂不分配执行人；分配后执行人与参与者各有不同权限。创建人存于 `tc_task.creator_id`，不重复写成员关系。

「发起审批 / 发起征询」弹窗只有两个要素:**目标状态**(审批时只读展示)与**交给谁**——交给谁是多选,
**选择顺序即处理顺序**(第一个人先办,余下依次,选完按 1、2、3 列出姓名);征询多选时可再选**逐级 / 并行**。
「交给谁」的候选 = **任务内的人**:创建人 + 参与者 + 执行人(右侧标出角色),去掉自己(**管理员除外** —— 管理员可以指派自己)。父任务要找人先自己加参与者,不反向依赖子任务的执行人;列表为空时提示先去「参与人」加成员。
多选控件(MultiSelect)的排版:搜索独占一行(带放大镜,清空靠右、仅有选中时出现),「已选 N 项 · 共 M 项」单独一行弱化显示,
其下才是已选标签与候选清单。

成员的写权限分两档：`memberAdd` 只要**任务相关方**（创建者 / 管理员 / 当前成员），陌生人不能把人拉进任务、更不能把自己加成执行人；`memberRemove` 仍是创建者或管理员。`taskGet.permissions.canAddMember` 与之同一判据，前端据此决定要不要显示「加成员」按钮。

新建 / 编辑任务的对话框按**四块**分区(区块标题 + `border-t` 细分隔线,不套卡片):
基本信息(名称 · 描述 · 流程模板 · 执行人 · 截止时间 · 优先级)、填报区(填报模板与带数下发,仅新建)、
链接区(清单式添加,站内 / 站外按 host 自动判定;每条带「预览」,**就地展开在链接下方**用 iframe 打开,不弹窗,展开的那条占满整行;站外站点若禁止嵌入会显示空白,可改走新标签)、附件区(任务相关方都能加)。编辑态只去掉填报区与「流程模板 / 执行人」。

`taskUpdate` 的 `payload` 字段与 `priority` 同口径：**不传 = 不动**、传 `null` = 显式清空、传对象 = 整块替换。不传 payload 时不会写内容修订。`payload.attachments` 里的文件 id 必须真存在且 `sys_file.status = 1`（已确认），创建与编辑路径共用同一道闸口；`attachmentUrl` 也只签已确认的文件（`status = 0` 是「已签发 PUT、对象还没上来」的中间态）。

任务创建时复制流程模板的状态与转移定义，后续修改模板不改变已创建任务。`status` 永远表示模板定义的任务业务状态；审批的处理状态在 `tc_action.status`，不会把框架临时状态写入任务。执行状态动作时，服务端依据状态、模板边、角色、成员关系和动作锁重新校验；`taskGet.permissions` 同时提供界面所需的可用动作。接口统一走 tRPC，并在 `src/lib/rbac.ts` 显式分类。

状态转移的可发起方只有三个任务角色:`creator`(创建人)/ `participant`(参与者)/ `executor`(执行者),数组 = 任一命中;任务非成员(且非创建人)不因模板边获得任何操作权。状态可标记为结束状态,进入该状态时事务内终止未完成动作及待发送通知;重新打开必须由模板显式定义转移边。

填报模板是**单版本**结构:版本表已并入 `tc_report_template`(`schema` 列更名为 `payload`,编辑即覆盖),绑定引用(`tc_task_report.version_id` 等历史列名)存的就是模板 id。`shared = 1` 全员可见、`0` 仅创建人与管理员;删除为软删 —— 已绑定任务的历史填报仍读得到 payload,只是不能再用于新任务/绑定。管理入口在「填报模板」独立页面(带只读预览)。

## 审批与征询

`tc_action` 是处理状态，不是历史流水；`tc_log` 才是不可变业务历史。根节点的 `root_action_id` 是自身 ID；多节点共用根 ID。串行流程只有当前节点为 `active`，其他节点为 `queued`；完成后在同一事务中激活下一人并创建通知。并行流程所有节点同时激活。

征询默认不锁任务状态，处理人回复意见时写入自由评论。审批锁定状态转移，但不改变任务当前状态；本期并行审批采用**全员通过**，全部通过后沿模板边推进，任一驳回则终止其他未完成节点，任务保持原状态。撤回审批会取消整条未完成流程，删除任务时取消其未完成动作和待投递通知。所有状态判定和动作结算按任务行锁串行执行。

站内通知与业务写入同一事务；SMS / Email 由独立 Worker 投递。查看时间与通知已读分开，未查看提醒只针对真实激活的节点。「轮到你了」不设「查看 / 收起」:通过 / 驳回 / 回复直接可点,动手时顺手记 `actionView`(提醒按它去重)。**通过 / 驳回都走弹窗**:各带一排常用原因(点一下填进输入框),通过的「意见」可留空、驳回「原因」必填;两者写下的意见都落成一条评论(`通过意见:` / `驳回原因:`)。手动催办、投递记录及失败重试详见通知中心文档。

## 日志规则

每次用户业务操作与 `tc_log` 在同一事务内提交或回滚；`sys_log` 是独立的全站审计台账。`from_status` / `to_status` 只记录该次操作真实发生的任务状态变化，没有变化时均为 NULL。发起审批的目标状态由流程**自动判定**(当前状态出发的审批边取模板顺序第一条,弹窗里不可选),目标与来源状态记录在 `detail`，不冒充任务状态变化。填报实时保存(600ms 防抖)不逐次写活动日志。建任务时附带的数据规则写入 `task.create` 事件 detail;其筛选条件详情只向任务相关方、创建人和管理员返回。

## 验证与启动

```bash
pnpm db:create             # MySQL 建表、索引与注释
pnpm db:dm:create-ba       # 达梦建表；需真实达梦实例
pnpm db:seed:task-close    # 默认流程模板
pnpm dev                   # Web 服务
pnpm worker                # 独立调度和通知投递
pnpm typecheck
pnpm check                 # 会自动写入格式修复
pnpm test                  # 使用 .env.local 所配置的测试数据库
pnpm build
```

MySQL 与达梦 DDL 均须同步维护；未连接真实达梦实例时不能以 MySQL 测试代替达梦验证。运行中的任务数据、模板和通知记录不得通过重新建表覆盖。
