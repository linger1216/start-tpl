# 任务闭环设计详解

> 面向要改这个模块的人。概览在 [`task-close.md`](task-close.md),填报专题在 [`task-forms.md`](task-forms.md)。
> 本文讲**为什么长成这样**、以及**改哪里会踩什么**。
>
> 代码入口:`src/integrations/trpc/routers/task-close.ts`(2902 行,46 个 procedure)。

---

## 1. 定位与边界

任务闭环是模板驱动的**通用协作内核**,不绑定业务:

| 它负责 | 它不负责 |
| --- | --- |
| 流程模板、快照、状态推进 | 具体业务字段的口径(交给填报模板) |
| 成员关系与任务级授权 | 系统级功能权限(交给 `lib/rbac.ts`) |
| 审批 / 征询两类动作 | 跨模块编排(交给调度模块) |
| 结构化填报与批次汇总 | 报表 BI |
| 活动日志 | 全站审计(`sys_log` 是独立台账) |

**关键取舍**:任务的前进动力来自**流程模板**(状态图),不来自代码里的硬编码状态名。派生项目换业务 = 换一张模板,不动代码。

│ lib/task-close-reminders.ts           │  Worker 侧未查看提醒
└──────────────┬───────────────────────┘
               │
┌──────────────▼───────────────────────┐

**为什么 `task-close-spec.ts` 单独存在**:`scripts/seed-task-close.ts` 是纯 tsx 脚本,不该为了一个字符串常量把整套 tRPC 运行时装进去。同理 `task-close-log.ts` 被前端和纯函数测试直接 import,不能碰 DB。

**为什么纯函数抽到 `lib/`**:填报校验、汇总、Excel 都是可测的确定性逻辑。放在 router 里既不能单测,也会把 xlsx 这种重依赖拉进 tRPC 的 import 图。

## 3. 数据模型(13 张 `tc_*`)

时间列口径:`tc_*` 全部用 `_at` 后缀(`created_at` / `updated_at` / `deleted_at`),与 `sys_*` 的 `_time` 两套口径**不要混**(见 `src/db/schema.ts`)。

### 3.1 流程模板

**`tc_workflow`** —— 可编辑的状态图模板

| 列 | 说明 |
| --- | --- |
| `id` | varchar(191)。内置默认模板固定为 `wf-default` |
| `payload` | json。整套 `{ name, statuses, initial, edges }` |
| `deleted_at` | 软删 |

`payload` 的形状(`WorkflowPayload`):

```ts
{
  name?: string,
  statuses: { value: string; label: string; terminal?: boolean }[],
  initial: string,
  edges: {
    from: string; to: string;
    who: ("creator"|"participant"|"executor"|"any")[];
    via: "direct" | "action";
    guard?: "report_submitted";
  }[]
}
```

`value` 落库、边引用;`label` 只做展示。**不存中文映射表** —— 状态名是业务数据,不是词表。

内置模板(`wf-default`)不允许删:`workflowRemove` 里硬拦。删光了建任务就没模板可选。种子还带一张 `wf-safety-check`(演示「`who` 换成 participant」的变体),它不是内置,可删。

两张种子模板的 `open → done` 都是 `via: "action"`;`done ↔ closed`、`closed → archived` 都是创建者的 `direct` 边。所以开箱即用的流程是「发起审批 → 发起人之外的人核验 → 创建者关闭」。

### 3.2 任务本体

**`tc_task`**

| 列 | 说明 |
| --- | --- |
| `id` | varchar(191) |
| `name` / `description` | 标题 / 说明 |
| `status` | varchar(32)。**永远表示模板定义的业务状态**,不写框架临时态 |
| `creator_id` | varchar(191)。创建人**不进 `tc_member`**,这是他的固有属性 |
| `due_at` / `priority` | 截止 / 优先级(`tinyint`,`0`=P0 … `2`=P2) |
| `payload` | json。内容区(块数组)+ 附件区 |
| `workflow` | json。**创建时从 `tc_workflow.payload` 复制的快照** |
| `deleted_at` | 软删 |

**快照是设计的核心**:之后改模板不影响已建任务。所以 `tc_task.workflow` 是自包含的,`taskGet` 不需要 join `tc_workflow`。

索引:`idx_task_status_created`(status)、`idx_task_creator_status`(creator_id, status)。

### 3.3 成员

**`tc_member`**

| 列 | 说明 |
| --- | --- |
| `task_id` / `user_id` | 多对多 |
| `role` | `participant` \| `executor` |
| `is_primary` | 主执行人标记 |

唯一键 `uk_member_unique (task_id, user_id, role)`。

⚠️ **这个唯一键带 `role`,意味着库层面允许同一人留两行**。限制在应用层:`memberAdd` 的去重键**只到「人」为止**(不带 role),否则同一个人能同时是参与者和执行者,`myRoles` 会算错、`taskTransfer` 的降级逻辑也会乱。

一个任务**至多一个执行人**。靠 `memberAdd` 里「已有执行人 → 拒绝」+ 行锁保证,不是唯一索引保证(`is_primary` 不在唯一键里)。

### 3.4 动作

**`tc_action`** —— 审批 / 征询的**当前处理节点**

| 列 | 说明 |
| --- | --- |
| `task_id` | |
| `serial_no` | 根节点写自己的 id;同一条流程的所有节点共用根 id |
| `parent_action_id` | 串行链 / 追问的父节点 |
| `is_locking` | 这条流程是否锁任务状态转移 |
| `from_status` / `to_status` | **只有根节点有值**;子节点两列都 NULL |
| `sequence` | 同链顺序,根为 0 |
| `created_id` / `handle_id` | 发起人 / 处理人 |
| `status` | `active` / `queued` / `done` / `rejected` / `cancelled` |
| `viewed_at` / `activated_at` / `last_urged_at` | 查看 / 激活 / 上次催办时刻 |

`tc_action` 是**处理状态,不是历史流水**;历史在 `tc_log`。

索引:`idx_action_task_serial`、`idx_action_handle_status`、`idx_action_parent`、`idx_action_unviewed`。

### 3.5 评论 / 日志 / 修订

**`tc_comment`** —— 自由讨论。文字 + 附件 + 结构化 @。**不是正式填报**。

**`tc_log`** —— 只增不改的活动日志。与业务写入**同一事务**提交或回滚。

`from_status` / `to_status` 只记**真实发生的任务状态变化**,没变化就是 NULL。发起审批的「想去哪」放在 `detail.intendedTo`,不冒充状态变化 —— 这是刻意的:`actionCreate` 不改任务状态,写进状态列会让流程脊显示假跳转。

**`tc_content_revision`** —— 说明的修订历史。唯一键 `(task_id, revision)`。创建任务时写 revision 1。

### 3.6 填报(6 张)

| 表 | 唯一键 | 职责 |
| --- | --- | --- |
| `tc_report_template` | — | 模板名称与创建人 |
| `tc_report_template_version` | `(template_id, version)` | **不可变**发布版本,`schema` 是 json |
| `tc_task_report` | `(task_id)` | 单任务填报:草稿、`revision`、`current_submission_id` |
| `tc_report_submission` | `(report_id, revision)` | 每次正式提交的不可变快照 |
| `tc_report_batch` | `(creator_id, request_id)` | 批次:模板版本、流程、截止、汇总配置 |
| `tc_report_batch_task` | `(task_id)` + `(batch_id, target_user_id)` | 批次与任务关联。**一个任务最多属于一个批次** |

版本不可变是关键:任务填报绑 `version_id`,模板改了也不影响已绑定的任务。`getReportVersion` 找不到就是数据坏了(直接抛)。

### 3.7 与调度 / 通知的关系

任务表**不直接写通知**。`createNotification` 在同一事务里写 `sys_notification` + `sys_notification_delivery`;SMS / Email 由独立 Worker 投递。详见 [`通知中心.md`](通知中心.md)。

## 4. 核心机制

### 4.1 who 协议

`edges[].who` 是一个**角色数组,语义是 OR**。判定函数 `whoAllows`:

| `who` | 结果 |
| --- | --- |
| `[]` | **false**(系统自带,前端不开) |
| 含 `"any"` | true |
| 含 `"creator"` 且 `task.creator_id === meId` | true |
| 含 `"participant"` / `"executor"` | 查 `tc_member` |

三种角色来源不同:`creator` 读 `tc_task` 列,另两个查 `tc_member`,管理员**不在这里判**(由调用方先判 `isAdmin` 跳过)。

### 4.2 三层权限

别再新增第四层。

| 层 | 判据 | 位置 |
| --- | --- | --- |
| **系统功能权限** | 菜单 / 权限点 | `lib/rbac.ts` 分类 + 中间件 |
| **任务级授权** | `who` 协议 + 成员关系 | router 内 `whoAllows` / `assertCanManage` / `assertTaskParticipant` |
| **界面按钮** | 服务端算好的 `permissions` | `taskGet.permissions`,前端只读不解释 |

**`permissions` 由服务端下发**是这套设计的关键:同一份判定同时给详情页按钮、后端拒绝、可用动作列表三处用,不会出现「前端能点、后端 403」。

`permissionsOf` 返回:`isAdmin` / `isCreator` / `myRoles` / `locked` / `transitions` / `actionTargets` / `canInitiateStatusAction` / `canInitiateConsult` / `canAddMember` / `canManageMembers` / `canUpdate` / `canRemove`。

成员写权限分两档:

- `memberAdd` —— **任务相关方**(创建者 / 管理员 / 当前成员)。陌生人不许拉人、更不许把自己加成执行人。
- `memberRemove` —— 仅创建者 / 管理员。

`canAddMember` 与 `memberAdd` 的 `assertTaskParticipant` **同一判据**,改一个必须改另一个。

### 4.3 状态机推进:`direct` vs `action`

模板的边分两种:

| `via` | 含义 | 谁执行 |
| --- | --- | --- |
| `direct` | 直接改状态 | `taskTransit`,立即生效 |
| `action` | 发起审批 | `actionCreate` → 对方 `actionRespond`,全部通过才落状态 |

**审批不立即改状态**。`is_locking = 1` 的根动作只是「占住这条转移」,任务 `status` 保持原值;全部节点通过后沿 `root.to_status` 推进,任一驳回沿 `root.from_status` 回退(实际就是不动)。

守卫 `guard: "report_submitted"` 要求任务存在当前有效填报。三处都检查:可用动作计算、发起转移、审批通过。**管理员也不能跳过模板边或守卫**。

### 4.4 动作树:串行 / 并行

一条流程的所有节点共享 `serial_no` = 根 id。根节点由 `handleId` 建,**后续节点由 `nextHandleIds` + `flowMode` 建**,一次调用落齐(`actionCreate` 事务内循环插入)。

```
根:  id=A, serial=A, seq=0, is_locking=1, from=open, to=done, active
  ├─ 子1: serial=A, parent=A,  seq=1                 ← 两种模式都这样
  └─ 子2: serial=A, parent=子1, seq=2 (serial)        ← 串成链
         serial=A, parent=A,  seq=2 (parallel)       ← 全都挂在根上
```

- **serial**:只有 `parent_action_id = 上一个节点` 才是链上的下一环;新建时 `status='queued'`、`activated_at=null`,不发通知。
- **parallel**:所有节点 `parent_action_id = 根`、`status='active'`、建时就发通知。
- 两种模式下 `is_locking` **全部继承根节点** —— 所以「还有没有未完成的锁定节点」这一句查询能跨整条流程数。

`activateNextAction` 按 `parent_action_id = 刚完成节点 + is_locking 相同 + status='queued'` 取 `sequence` 最小的一个,`for update` 锁住再激活并发通知。因为串行链是「父指向上一环」的链表,这一步天然只会取到唯一后继。

**追问**(`parentActionId` 指向一个 `active` 动作):只有当前处理人能发起(管理员不豁免),`serial_no` 继承父、`sequence = 父 + 1`、`is_locking = 0`,**不推进任务状态**;且不允许同时带 `nextHandleIds`(多人流程只能从任务发起)。

`handles = [handleId, ...nextHandleIds]` 整体去重,同一个人不能在一条流程里出现两次。

### 4.5 锁语义

**「任务被锁」= 存在 `is_locking = 1` 且 `status ∈ (active, queued)` 的动作**(`isLocked`)。

锁定期:

- `taskTransit` 拒绝(「有未完成的审批动作,任务被锁定」)
- `actionCreate` 的审批分支拒绝(不能并发发起第二条审批)
- `permissionsOf` 的 `locked = true`,且**遍历模板边时直接 `break`** —— 返回的 `transitions` / `actionTargets` 全空,前端拿不到可点项,不是「拿到再禁用」

**锁守卫对管理员一视同仁**。放行会留下一个 `to_status` 与任务状态对不上的活动作。

**答复权也不给管理员**:`actionRespond` / `actionView` / `actionReply` 只认 `handle_id === me.id`。审批「谁被指派谁签」,管理员代签会让日志里的处理人失真。管理员的特权只在**发起 / 撤回 / 催办 / 改状态 / 管成员**这几处。

> ⚠️ **历史遗留**:更早的版本把锁实现成「发起审批时把 `tc_task.status` 硬写成 `"pending"`」,该机制已随 `0705f13` 移除,但没有回填脚本。**如果库里还有那个时期发起的审批,任务会卡在 `status='pending'`** —— 它既不是模板里的状态,也永远匹配不到 `root.from_status`。模板项目一般是新建库,无此风险;接管老库要先跑一句 `select` 排查。

### 4.6 事务与并发

所有改状态的路径都走 `db.transaction` + 行锁。

**加锁顺序固定:先任务、后动作。**

```ts
lockTask(tx, id)      // select ... for update
lockAction(tx, actionId)  // 先探 task_id,再 lockTask,最后锁 action
```

`lockAction` 先只读 `task_id`(免全表锁),再按同样顺序加锁,所以两条路径互不等待死锁。

其他并发点:

- `memberAdd` / `memberRemove` / `taskTransfer` 都在 `lockTask` 之后才查「已有几个执行人」,所以并发加执行人只会成功一个。`taskCreate` 不需要锁 —— 行还没存在,执行人唯一性在校验阶段就拦了。
- `reportSaveDraft` 用 `revision` 乐观锁,不是行锁:`report.revision !== input.revision` → `CONFLICT`。
- `reportBatchCreate` 锁 `sys_user` 行 + `(creator_id, request_id)` 唯一键,做幂等。

### 4.7 活动日志

16 个事件码,四类前缀(`task` / `action` / `comment` / `member`,外加 `report`)。

**类别不落库** —— 由 `logCategoryOf()` 从事件码前缀现算。存了就是第二个真源,迟早和 `event` 打架。

写入口只有一个:`logTaskEvent(tx, {...})`,必须在业务事务内调用。文案在 `describeLog(item, ctx)` 里按事件码派生,**中文是读取时算的**(库里只存英文码和状态 value)。

加事件码要同步改三处:`lib/task-close-log.ts` 的数组 + 界面注册表 `task-close-log.tsx` 的图标 + `doc/task-close.md` 的表。

`describeLog` 的 `default` 分支显示码本身 + 「未知事件类型」,不白屏 —— 但**新事件码没加分支就是 bug**,已有测试兜住 `report.*`。

### 4.8 链接块与修订

`tc_task.payload.links` 是**有序块数组**,每块就一个 `url`(`{ kind: "link", url }`)—— 有序是因为一条任务可能挂多个链接。

**站内 / 站外不存库**:渲染时按 host 判定(`isInternalUrl`)—— 相对路径(`/settings/users`)算站内走当前窗口,
绝对 URL 的 host(含端口)与当前页面一致也算站内,其余站外新开标签页。老数据的 `ref` 块(内部页面)在读侧折成
链接(路径 + 查询串拼回 URL),内容不丢;文字 / 表格块已取消,渲染成占位。

渲染**必须容错**:`parseBlock` 遇到不认识的 `kind` 返回 `null`,前端画占位。老客户端不该因为新块白屏。

`taskUpdate` 的字段语义统一为:

| 入参 | 含义 |
| --- | --- |
| `undefined`(不传) | **不动原值** |
| `null` / 空串 | 显式清空 |
| 有值 | 改值 |

`payload` 不传时**不写修订**。早先无条件 `normalizePayload` 会把只改名字的调用连内容区和附件一起清空,还写一条空修订 —— 这是修过的坑。

只有 `payload` 真变或 `description` 变才写 `tc_content_revision`(用 `stableJson` 键排序比较)。

### 4.9 附件链路

内容区 / 评论的附件都只存 `sys_file.id`,不存字节。(填报模板的字段类型不含文件,填报不带附件。)

**`attachmentUrl` 为什么不复用 `file.url`**:`file.url` 按 `/settings/files` 页面码授权,任务页调不到;放开到任务页又等于「任何登录用户凭 id 取任意文件」。所以它先确认 `fileId` 确实挂在这条任务上 —— 当前 `payload.attachments`,或(仅任务相关方可查)历史修订里的附件,或评论附件 —— 再签地址。

只签 `sys_file.status = 1`(已确认)的文件。`status = 0` 是「已签发 PUT、对象还没上来」的中间态。

### 4.10 填报:模板 → 草稿 → 提交 → 退回

```
tc_report_template ──< tc_report_template_version (不可变)
                                   │
tc_task ──── tc_task_report ───────┘  (status: draft | submitted | returned)
                  │
                  └── tc_report_submission (每次提交一份不可变快照)
```

- **草稿**:`reportSaveDraft`,revision 乐观锁。只读字段不许改(与 `defaultValue` 逐块比较)。
- **提交**:`reportSubmit`。校验通过才新增快照,`current_submission_id` 指向最新。
- **退回**:`reportReturn`。`status = returned`,`current_submission_id = null`,`revision + 1`,旧快照保留。
- **幂等重提**:同 revision 且已提交 → **校验提交人是不是自己**,是才返回原 id。换人后旧 revision 重放得 `CONFLICT` —— 否则会把上一位执行人的提交当成自己的。

**批次关闭 / 超截止**后不接受新提交。已提交的保留。

提交不自动完成任务;完成由流程动作和守卫决定。

### 4.11 批次与汇总

批次**不是父任务**:不进 `tc_task`,不影响各任务状态。它只是「一次下发」的记录。

```
tc_report_batch ──< tc_report_batch_task >── tc_task
```

创建时**单事务**内:建批次 → 逐个建任务(含成员、填报、通知)→ 建关联。失败整体回滚。

**幂等键** `(creator_id, request_id)`:同 key 同 hash 返回原批次(`created: false`),同 key 不同 hash 得 `CONFLICT`。

汇总(`summarizeTaskReports`)是**纯函数**,三档策略:

| 策略 | 行为 |
| --- | --- |
| `APPEND_ROWS` | 所有行平铺,每行带完整来源 |
| `MERGE_BY_KEY` | 按业务键合并;同键字段值冲突进 `conflicts[]` |
| `AGGREGATE` | 按业务键分组,对数值字段 `sum` / `count` / `average` |

**汇总是算出来的,不落库**:不存第二份真源。每行都带 `sources[]`(taskId / executorId / submissionId / submittedAt / rowIndex),任何一行都能追回原始提交。

每次 `reportBatchSummary` 都重算整批。批次规模是「一次下发几十个任务」量级,翻页重复计算可接受 —— 真成瓶颈再加缓存,**先有度量**。

### 4.12 通知与提醒

任务相关通知全部走 `createNotification(tx, ...)`,与业务同事务。

通知类型:`action.assigned` / `action.urged` / `action.unviewed` / `comment.mentioned` / `report.assigned` / `report.submitted` / `report.returned`。

**所有任务通知的 payload 都带 `path`**(`taskPathOf(taskId)`),铃铛点进去才能跳回详情页。

**未查看提醒**在两处:

- 主动:`actionView` 写 `viewed_at`,停止后续提醒。
- 被动:`lib/task-close-reminders.ts` 的 `checkUnviewedActions`,Worker 每 60 秒扫一次,在激活后 **60 / 180 分钟**各发一条。幂等键 `action.unviewed:<actionId>:<1|2>`。两轮都发过之后再扫也不再重复。

Worker 链路:`scripts/worker.ts` 注册 `task-close.unviewed`(间隔 60 s)→ `scripts/job-runner.ts` 的 handler map 指向 `checkUnviewedActions`。`checkUnviewedActions` 先按覆盖索引捞出「`active` + 未查看 + 激活已超 60 分钟」的动作 id,再逐个进 `checkActionReminder` 加行锁、二次校验、两轮补发。所以扫描本身不做写,幂等靠 `dedupe_key`。

`checkActionReminder` **用 `for update` 而不是「UPDATE 看 affectedRows」** —— 后者只在 mysql2 带 `FOUND_ROWS` 时成立,达梦的 `rowsAffected` 语义未验证,一旦按真正变更行数计会恒返回 0,两条提醒静默不发。

手动催办 `actionUrge` 有 30 分钟冷却(`TASK_URGE_COOLDOWN_MINUTES`),走 `last_urged_at` 条件更新。

## 7. 全链路示例:一次审批

```
创建人 A 建任务(T 处于 open)
  ↓
执行人 B 发起审批 → actionCreate(taskId, toStatus: "done", handleId: C)
  ├─ 校验:open → done 有 via=action 边;B 命中 edge.who
  ├─ 写 tc_action:A(id=A, serial=A, seq=0, is_locking=1, from=open, to=done, status=active)
  ├─ 通知 C(action.assigned)
  └─ 写 tc_log:action.create,detail={intendedTo:"done", intendedFrom:"open"}
     ↑ 任务 status 仍是 open(审批不改状态)

C 答复 → actionRespond(approved: true)
  ├─ 校验:task.status === root.from_status(open),且守卫通过
  ├─ action.status = done
  ├─ 查剩余活跃锁定节点 → 没了
  ├─ task.status = root.to_status(done);若 done 是 terminal → cancelLiveTaskActions
  └─ 写 tc_log:action.respond,from=open,to=done
     ↑ 这才是**真实的**状态变化,所以写进状态列
```

## 8. 设计决策速查

| 决策 | 为什么 |
| --- | --- |
| 流程存快照而非外键 | 改模板不影响在途任务 |
| `tc_action` 是状态不是流水 | 查「谁待办」要快;历史在 `tc_log` |
| `who` 数组 = OR | 一条边可开放给多角色,不必建多条 |
| `permissions` 服务端算 | 前后端同判据,不会「能点不能调」 |
| 汇总不落库 | 避免第二份真源;每行带来源可重算 |
| 填报版本不可变 | 任务绑定的 schema 永远可解释 |
| 批次不是父任务 | 不影响各任务状态,语义干净 |
| 日志类别现算 | 存了就成第二真源 |
| 附件只存 id | 权限收口在 `attachmentUrl` 一处 |

## 9. 已知边界

1. **锁机制历史遗留**:旧版把 `tc_task.status` 写成 `"pending"`,已移除但没有回填脚本。接管老库先用 `select id, status from tc_task where status not in (模板里的 value)` 排查。
2. **`reportBatchSummary` 每次翻页重算整批**。批次规模小,暂可接受。
3. **`notice.history` 按 `sys_notification_delivery.created_at` 排序,该列不是索引前导列**。管理页 + `limit ≤ 500`,真慢了再加索引。
4. **`checkUnviewedActions` 每次全量扫未查看动作**。走 `idx_action_unviewed` 覆盖索引,活跃动作天然是少数。
5. **`tc_member` 唯一键带 `role`**:库层面允许一人两行,靠应用层去重。若将来有第二条写入路径,要同样去掉 role 判重。
6. **达梦**:13 张 `tc_*` 表在 `scripts/create-better-auth-tables-dm.ts` 同步维护。**未在真实达梦实例上验证过的改动,不能拿 MySQL 结果代替**。
