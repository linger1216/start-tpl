# RBAC 权限模型(部门 / 角色 / 菜单可见性)

> 本文原在 `AGENTS.md` 里,2026-09 按「精简 AGENTS」的约定搬到这里(**内容一字未改**)。
> 什么时候看它:动权限判定、`sys_user_role` / `sys_role_menu`,或 `/settings/{roles,users,departments}` 三页时。

**"部门当组织用",但走的不是 Better Auth 的 organization 插件** —— 那套是"选中一个当前组织 + 租户隔离",
而这里要的是"**同时属于多个部门 + 角色给权限**",语义不同(而且它会往 session 上加一个用不上的
`active_organization_id`)。所以是项目自己的五张表:

```
sys_dept(树)                         上海公司 / 武汉公司(可嵌套)—— 纯组织架构
sys_role(全局定义)                          管理员 / 员工 / 开发 …   ← 不随部门数增长
sys_user_dept(user_id, department_id)  张三 ∈ 上海公司、武汉公司(**不带角色**)
sys_user_role(user_id, role_id)                张三 → 管理员、普通员工(**权限 = 这些角色的并集**)
sys_role_menu(role_id, menu_id)                角色能看见哪些菜单 / 能用哪些按钮
```

**权限标识 = `域:资源:动作`(三段小写),每段可整段写 `*` 通配。** 例:`sys:role:add` / `sys:role:*` / `sys:*:*` / `*:*:*`(全部权限,**含以后新增的菜单**)。
- **通配在读取时展开**,只改一处:`lib/rbac.ts` 把模式命中的菜单行当成"被授权"再走同一套祖先补全 —— 所以
  `use-perms.ts` 与各页面**一行都不用改**,`*:*:*` 也自动覆盖未来新增的域/菜单(不用回来补勾);想收窄再加一条模式行。
- **域 = 一级模块 key**,允许长新域;受控的是**形状不是取值** —— 菜单接口的 `perm` 用 `PERM_FORMAT` 挡住
  两段 / 大写 / 半截通配(`sys:ro*`)。⚠️ 段数不符的模式**永远匹配不到**,症状是"勾了没权限",极难查。
- 运维权限点两条:`*:*:*`(通配,种子授给系统管理员)与 `sys:user:impersonate`(切换用户),挂在隐藏分组「运维工具」下。

- **角色全局定义、按人分配** —— 这是"角色爆炸"的解药:角色行数**不随部门数增长**
  (4 种角色在 100 个部门里也只有 4 行)。角色**与部门无关**(早期版本把角色记在部门成员上,
  结果是"同一个人在不同部门才能有不同角色",那是没必要的复杂度 —— `sys_user_dept.role_id`
  已经删掉,分配入口收在「用户管理 ▸ 编辑」里)。
- **并集**:一个人所有**角色**的授权取并集 —— **没有"当前部门",也不需要切换**。
  计算在 `lib/rbac.ts` 的 `effectiveMenusFor(userId)`(它只 join `sys_user_role` + `sys_role`,不看部门):它**只吃 `userId`**,与"怎么拿 userId(会话)"解耦,
  所以单测可以直接喂一个 id,不必造 HTTP 会话。
- **菜单与按钮同一张表**:`sys_menu.type` = 1 目录 / 2 菜单 / 3 按钮,`perm` 是权限标识(如 `sys:role:write`)。
  按钮**不进侧边栏**(`buildNavTree` 会过滤),但作为叶子出现在角色授权树里
  (`PermissionPicker` 给它一个「操作」徽章);授权后它的 `perm` 进入用户的权限集合 ——
  前端 `useHasPerm(code)` 认它。**按钮行的 `path` 用不指向路由的占位值**
  (沿用"纯分组也给占位 path"的既有约定,`path` 保持 not null + 唯一)。
- **勾子节点要自动补全祖先**:侧边栏是按 `parentId` 拼树的,只授权一个深层子菜单会让那一枝无处安放
  ("勾了却看不见")。写入(`role.setMenus`)与读取(`rbac.ts`)用同一份 `withAncestorIds()`。
- **未启用不过滤**:`sys_role_menu` **一条都没有** → 全部菜单可见 + `perms = null`(一律放行)。
  这是刻意的兜底:新项目/新库还没配权限时,不能把管理员自己锁在门外。配了第一条授权就立即生效。
- **认不到人 → 失败关闭**:权限体系开着但拿不到会话 → 空菜单 + `perms = []`(不是 `null`)。
- **隐藏 ≠ 禁止**:本轮只做"可见 / 不可见"(前端)。**服务端还没有路由级 / 接口级拦截** ——
  真要拦,在对应 procedure 里查同一份权限集合(挂点是 `lib/rbac.ts` 的 `effectiveMenusFor`)。
- 三页页面:`/settings/departments`(树 + 成员,含加人/移出;角色只读展示)、`/settings/roles`(台账 + 权限点勾选)、
  `/settings/users`(账号台账 + **建 / 改 / 删** + 在**编辑弹窗里用多选框分配全局角色与部门**)。**账号仍归 BA**:
  - `create` 转调 `auth.api.signUpEmail`(密码哈希只有它会写);
  - `update` 改**姓名 / 邮箱 / 头像(`image`)/ 邮箱已验证(`email_verified`)**,
    并**覆盖式**保存**角色**(`roleIds`)与**部门**(`departmentIds`)—— 传进去的就是最终状态,
    四个字段都**必传**(少传一个就会把那一项清空;这也是为什么它们是必填而不是可选)。
    改密码是 BA 的 `changePassword`(要本人/邮件往返),不在这里假装能做;
    `sys_user` 的其余列(`id` / `created_at` / `updated_at`)是系统列,不开放编辑 —— 这就是"能编辑的字段"的全部;
  - `remove` 先清 session / account / 部门成员再删用户,**并拒绝删自己**(删掉自己的会话 = 立刻掉线)。
  ⚠️ `signUpEmail` 会顺手建一个会话并下发 cookie —— 建完**必须立刻删掉那个会话**,
  否则下一个请求就用新用户的身份了(`tests/user-crud.test.ts` 专门断言这一点)。
  ⚠️ 外键上虽然写了 `on delete cascade`,但 session / account 两张表**不归我们建**,别依赖它们的级联 —— 显式删。

**演示数据:`pnpm db:seed:rbac`**(幂等)。跑完可以直接点着看:

| 账号 | 密码 | 能看到什么 |
| --- | --- | --- |
| `admin@example.com` | `Passw0rd123` | 上海公司 = 系统管理员 → 全部 9 个菜单 + 两个按钮权限点(角色页的「新增 / 删除」可见) |
| `zhangsan@example.com` | `123456` | 两个全局角色:部门主管 + 普通员工(部门归属:上海公司、武汉公司)→ 6 个菜单(**两个角色的授权取并集**)、**没有按钮权限(角色页那两个按钮不可见)** |

> 密码:建出来的账号默认是 `Passw0rd123`,但库里**已经被手工改过** —— `zhangsan` 与后来那批测试账号是 `123456`,
> 只有 `admin@example.com` 还是 `Passw0rd123`(见「认证」那节的改密码做法;种子脚本里的常量没跟着改)。

⚠️ **跑过它之后权限体系就"启用"了**(`sys_role_menu` 不再为空):**没有任何角色的账号将看不到任何菜单**(部门归属不影响权限)。
要回到"未启用、全放行"的状态,把 `sys_role_menu` 清空即可。

**数据权限(行级)是下一轮**:`data_scope` 记在角色上,按「角色的范围」取并集 ——
   张三 → 管理员 → 全公司数据
        → 员工   → 仅本人数据        并集 = 全公司 ∪ 他本人的数据
现在**不加那一列**(没人读的列就是 AGENTS 禁的「伪扩展点」);`sys_user_dept` 已经承载了
将来做这件事所需的全部信息,到时只需要给 `sys_role` 加列 + 写一个 `where` 构造器。

## 行级数据权限(数据范围)—— 2026-09 落地

> 本节是**正式口径**,取代上面「规划」里更早的设想。核心一句话:
> **档位词存在角色上,范围永远在部门(组织)树上算出来。**

### 一、唯一载体:`sys_role.data_scope`

| 取值 | 中文 | 怎么算(只用 `sys_dept` 已有的 `parent_id`) |
| --- | --- | --- |
| `all` | 全部数据 | 不过滤(**默认值**,升级后可见范围一行不变) |
| `self` | 仅本人 | 业务表 `create_by` = 我 |
| `dept` | 本部门 | 我所属部门集合(`sys_user_dept` 多对多,可能多个) |
| `dept_below` | 本部门及以下 | 我所属部门 + 各自**子树** |
| `up:N` | 往上到「**从根往下第 N 层**」及以下 | 从我所属部门**往上**找到第 N 层的祖先(含自己)⇒ 它 + 子树 |

**为什么 `up:N` 长这样**(而不是"往上找街镇类型"):
本项目的 `sys_dept` 与用户-部门关系都是**区里推过来的只读数据** ⇒ **一个字段都不加**。
所以锚点写成**角色上的一个数字**,层号从根(第 0 层)往下数 ——
树是 `区(0) → 街镇(1) → 部门(2)` 时,`up:1` 就是「本街镇及以下」,
**一条「网格长」角色即可覆盖 14 个街镇**,不必建 14 条角色。

**三条实现纪律**:

1. **值域用正则挡死**(`SCOPE_FORMAT`,`lib/data-scope.ts`):形状不对就当没配 —— 与 `PERM_FORMAT` 同一套纪律;
2. **fail-closed**:往上找不到目标层 / 没有部门 ⇒ **空集合**(什么都看不到),不是放开;
3. **多角色取最宽**(`all` > `dept_below` > `up:N` > `dept` > `self`);
   **但"一个角色都没配"⇒ 不收窄**(返回 `all`)—— 与 `effectiveMenusFor` 的 `perms = null`
   「权限体系未启用一律放行」同口径。要收紧某人,**就给他配一个角色**,那才是表达意图的地方。

### 二、业务表的约定

| 字段 | 服务哪档 | 没有会怎样 |
| --- | --- | --- |
| `dept_id`(或能 join 到部门) | `dept` / `dept_below` / `up:N` | 这几档对它不过滤 |
| `create_by` / `owner_id` | `self` | `self` 档对它不过滤 |

**不强制每张表都加** —— 字典 / 参数 / 菜单这类全局表**就是不该过滤**(那不是漏,是明确不需要)。

### 三、代码怎么用

```ts
// 1) 拿到这个人的生效范围(展开后一律是"一批部门 id")
const { scope, departmentIds } = await scopeOf(userId);

// 2) 拼条件(谁表里有哪列就用哪个构造器)
const where = combine(
  deptCondition(bizGrid.deptId, departmentIds),          // 有部门列
  ownerCondition(bizGrid.createBy, userId, scope),        // 有负责人列
  userIdsOfDepartments(departmentIds),                   // 多对多(如 sys_user 自己没部门列)
);
```

**两条硬规矩**:

> 1. **统计 / 导出 / 多表 join 必须走同一组辅助函数** —— 这是行级权限最经典的越权通道,禁止手写 where;
> 2. 业务查询的入口集中在列表 / 统计 / 导出三处,新增一处就要在 PR 里对一眼这条。

**当前落点**:`user.list`(本模板里唯一有组织归属的业务数据)。

### 四、第二期(讨论过、暂不实现)

| 题目 | 需要什么 |
| --- | --- |
| **`custom` 指定若干部门**(跨互不从属的组织) | `sys_role_dept(role_id, dept_id, include_below)` + 角色表单部门多选 |
| **层级不规整 / 想按"类型"锚定**(如直接说 `street`) | 加**我们自己的** `sys_org_type(dept_id, type)` 标注表(列名 `type`,与 `sys_menu.type` 同口径)—— **仍然不碰 `sys_dept`** |
| **跨轴精确并集**(既看本部门、又要看"我负责的那几条") | 现在取最宽;精确版按角色展开成多条规则再 OR(改动只在这一个文件) |
| 借调(人在 A 部门、管 B 的事) | 现在已可表达:把业务行的 `create_by` / 负责人指给他 + 给他一档 `self` |

### 第二个真实落点:`demo_grid`(Demo › 网格履职)

| 身份 | 条件 | 实测(真实数据 71 条) |
| --- | --- | --- |
| 队员(`self`)| `owner_id = 我` | **4 条**(七宝镇 7 条里指派给他的)|
| 队长(`up:2`)| `town_id IN (本街镇及以下)` | **7 条**(整个七宝镇)|
| 区(`all`)| 不过滤 | **71 条** |

⚠️ **写操作也套同一个范围**(`update` / `remove` / `assign` 都先 `visibleRow` 校验)——
只在 `list` 上套范围 = 队员拿到别人的 id 照样能改能删(IDOR)。`tests/demo-grid.test.ts` 钉住了这一条。

人员映射靠**数据**而不是角色:网格表的 `owner_id` 指派给谁,谁就是负责人 ⇒ **68 个网格 0 个新角色**。
