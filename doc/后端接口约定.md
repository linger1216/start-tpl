# 后端接口约定(tRPC)

> 定位:这份文档回答「加一个接口 / 改一个接口时,怎么算合格」。它来自一次**全量接口审阅**
> (53 个业务 procedure + 1 个演示 router、逐个人工过、并核对前端调用点),把当时的结论固化成规矩。

## 一、每个接口都要能回答"它为什么单独存在"

写新接口前先自问:它是不是**另一个接口的另一种投影**?如果是,优先加参数而不是加接口。
三条判据:

1. **不同粒度 = 可以有两个接口**(新建向导要「读字段」、要「预检」是两次人机交互);
   但**同一件事的实现只能有一份**(两者都必须落在 `lib/sync/adapters` 上,不许各自写一遍取数);
2. **同一份数据的两种视图 = 一个接口 + 参数**(例如「执行日志」按 `kind` 过滤),不要拆成互不相干的接口;
3. **只有"批"与"单"两种语义**时,给**批**一个正经接口(`*Many`),不要让前端循环调单条 —— 见第三节。

## 二、一条业务逻辑只允许一个实现(落地口径)

| 事情 | 唯一实现 | 谁在用 |
| --- | --- | --- |
| 落 `data_raw`(幂等 + 版本留痕 + **批内同主键收口**) | `lib/sync/landing.ts` 的 `insertRawBatch` | 接口/库表同步 **与** 文件导入(`source.importRows`) |
| 档案属性清单的读写 | `lib/governance-rule/field-registry.ts` | 规则执行器、档案页增删改、人工复核、导入 |
| 显示名映射(键 → 显示名) | 同上的 `fieldLabelMap` / `fieldLabelMaps` / `fieldLabelMapOf` | 档案列表、详情、规则表单的落点下拉 |
| 执行日志行 → 接口出参 | `lib/exec-log.ts` 的 `execView` | 执行日志「定时任务」、规则「执行历史」 |
| 同步配置的解析与校验 | `lib/sync/types.ts` 的 `parseSyncConfig` | 数据源表单预检、预检、同步、同步状态 |
| 时间格式化 | `lib/time.ts` | 全部(禁止 `toISOString()` 当人看的时间) |

**判据**:同一段逻辑如果在两个接口里各写了一遍,`grep` 一下就会出现两处相似代码 —— 那时不是"复制粘贴方便",而是"以后必然有人只改一处"。

## 三、批与单:能批就批

- `entity.deleteMany` / `source.rawDeleteMany`:一条请求删一批 → **一次事务 + 一条审计**;
- 前端**禁止**用 `for (const id of ids) await remove({id})` 这种循环:会产生 N 次往返、N 条审计,
  中途失败还会留下"删一半"的状态;审计里也回答不了"这次到底删了哪些"。
- 批量接口都要有上限(`max(200)` 这类),防止一次把库拖垮。

## 四、列表接口的两种形状(刻意如此,不是不统一)

| 形状 | 什么时候用 | 例子 |
| --- | --- | --- |
| `{ rows, total }` | 数据量大 / 需要分页 / 需要"匹配 N 条" | `entity.list`、`source.rawList`、`review.list` |
| 裸数组 | **目录型小表**(几十行、一次取完、前端自己分页) | `source.list`、`menu.list`、`dict.list`、`config.list` |

规则:**同一个接口不允许一半分页一半不分页**;目录型表一旦超过几百行,就该升级成 `{ rows, total }` 并加分页参数。

## 五、刻意保留的"看起来重复"(别删)

| 保留项 | 为什么 |
| --- | --- |
| `source.probeFields` / `source.precheck` / `source.probeSync` | 三次人机交互粒度不同(读字段生成映射 / 四步预检 / 已保存源的体检),底层实现同一份 |
| `source.syncStatus` 与 `source.list` | 前者是**派生视图**(凭据是否就绪、水位、最近一次结果),后者是目录 + `syncConfig` 原样(编辑表单回填要它) |
| `job.list` / `rule.runs` | 同一张执行日志表的两个页签(`stage` / `action` 不同、补充字段不同),公共字段已收进 `execView` |
| `sync_config.columns`(库表源只拉指定列) | 有**缺陷修复史**(曾经的 bug:白名单外的列也落了 attrs)+ `test:sync` 有用例;界面不暴露是刻意的 —— 没人会配的东西不加开关,但**能力本身保留** |
| `todos.*` | 模板自带的示例 router,`routes/(main)/demo/trpc-todo.tsx` 在用;删 demo 时一起删 |

## 六、自检清单(改完接口对一遍)

1. `pnpm typecheck` / `pnpm check` 0 error;改了执行日志(表名 / 阶段 / 动作)后,跑一次
   **`pnpm db:migrate-exec-log`**(幂等)+ `pnpm check:schema-drift`(含列检查);
   新增阶段/动作时,先改 `src/lib/exec-log.ts` 的常量表,再用 `isValidExecAction` 约束写入;改了 `src/db/*.ts` 里的表/索引定义后,再跑一次
   **`pnpm check:schema-drift`**(逐索引比对 drizzle 声明与真实库:唯一性降级、列不一致、库里多出来的索引都会报);
   ⚠️ 注意 `pnpm db:push` 在当前库上**跑不通**(drizzle-kit 0.31 的 MySQL 内省遇到 `data_alias` 上的函数索引会报
   `Expected string, received null`,与本次 schema 改动无关,回退后同样报错)—— 所以"以库为准"的对账只能靠这个脚本;
2. 新增/改动的 procedure 被 `test:scenarios` 的**入口扫描**覆盖(它要求 55+/55+ 全部有调用与日志,见下);
3. 新逻辑若属于第二节表格里的任何一类,必须是**调用**已有实现,而不是复制;
4. 批量语义的接口要有上限、要写**一条**审计;
5. 跑 `pnpm coverage:lines`(后端行覆盖 + 入口/日志覆盖)确认没退化。

## 七、并发:融合走**进程内单道队列**(并发 = 1)

### 问题

建档/融合是"**读档案 → 在内存里按策略算 → 整对象写回**"。两个数据源同时对同一条档案融合时,两个执行流的读-算-写会交错:

```
A 读(旧快照) ─┐
B 读(旧快照) ─┤          两边都基于同一份旧值算
A 写 attrs=..., origins=[old, rA]
B 写 attrs=..., origins=[old, rB]   ← A 的字段改动与来源记录被整对象覆盖(丢失更新)
```

症状很隐蔽:**两边都报成功**,只有把两条审计的 before/after 拿来对账,才发现有一处"改了又变回去"。

### 做法

`src/lib/fusion-lane.ts` 一条 promise 链,`runInFusionLane(task)` 让所有融合任务**按到达顺序逐个执行**。

**必须遵守的一条**(否则排队毫无意义):

> 任务里要**重新读取**它将要写的数据 —— 读的位置必须在进道之后。
> 把 `select` 留在道外、只把写排队,排的就只是"用旧快照去写"。

执行器里的对应写法见 `lib/governance-rule/executors/source-extract.ts` 的 `processRow`:`select ... from data_entity` 与 `update` 在同一个任务闭包里。

### 边界(必须知道)

- **只在单进程内成立**。dev server 与测试脚本/定时任务是不同进程时,仍可能丢失更新;
  跨进程要解决就得加 **版本列 CAS** 或 **队列表**(加一列/一张表)。
- 首次建档的跨进程竞争由 `uk_entity_biz` 唯一键 + 执行器的 `insert ignore` 兜住(记"并发…留到下批",不丢不重)。
- 队列有上限(`FUSION_LANE_MAX_DEPTH`,默认 50):堆满时 `rule.execute` **明确拒绝**并提示排队数,不静默等待。

### 为什么不用数据库侧的并发原语

目标库可能从 MySQL 换成达梦或 PostgreSQL,所以刻意不引入任何方言相关的并发手段:
不用 `SELECT ... FOR UPDATE`、不用 `UPDATE ... ORDER BY ... LIMIT`、不用 `GET_LOCK`,也不加表/加列。
单道队列是纯 JS,**零方言、零依赖、零 schema 变更**。

### 现状里真正的"换库热点"(与并发无关,但换库前要处理)

| 用法 | 位置 | 换库影响 |
| --- | --- | --- |
| `json_table` / `json_keys` | `lib/governance-rule/field-registry.ts`(5 处) | 最大热点:PG 要换 `jsonb_object_keys` / `json_array_elements`,达梦需单独验证 |
| `.ignore()`(INSERT IGNORE) | `landing.ts`、`audit.ts`×2、`source-extract.ts`、`link.ts`、`review.ts`(6 处) | drizzle 的 PG 方言是 `onConflictDoNothing()` |
| `onDuplicateKeyUpdate` | `field-registry.ts` | PG 方言是 `onConflictDoUpdate()` |
| `json_extract` | `lib/sync/run.ts` | 按方言改 SQL |
