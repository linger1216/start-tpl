# 数据权限(行级可见范围)

> 什么时候看它:动 `sys_data_policy` / `sys_data_plugin`、写新的读接口、或改
> `/settings/data-scope`、`/settings/data-plugins` 两页时。
> 功能权限(能不能进这个页面 / 能不能用这个按钮)是另一回事,看 `doc/rbac-权限模型.md`。

## 一句话

**功能权限答"能不能调这个接口",数据权限答"调了之后能看见哪些行"。**

判断条件**相对发起人**表达,不和具体的人绑定:

```
张三 属于 闵行区法院      ⇒ 规则里写的是「我的部门及以下」,不写「闵行区法院」
换个人登录,同一行规则自动换一批行
```

所以规则表里**只存 `role:<角色 id>` 这种引用**,请求时用 `roleIdsOf(userId)` 展开 ——
不存在"给 38 个账号各写一行"的物化。

## 两张表

```
sys_data_policy  规则:谁(主体) + 哪张表(资源) + 怎么筛(判据列 + 引哪个插件)
sys_data_plugin  值域插件:算出一组值(内置的按上下文算;用户自建的就是一份写死的清单)
```

`sys_data_policy` 只有**两种合法组合**(越界由 `validatePolicyCombo()` 在写接口拦下):

| 组合 | `column` | `plugin_key` | 编译出的条件 | 含义 |
| --- | --- | --- | --- | --- |
| 整类可见 | 空 | 空 | 不产生条件 | 这张表的全部行 |
| 给值 | 有 | 有 | `` `column` in (插件算出的一组值) `` | 例:街镇 ∈ 我的部门及以下 |

> v1.3 (m18228) 改动:插件不再有「给行 / 给值」两种形态,也没有 `domain` / `resource` 字段 —
> 详见「[v1.3:插件只回答"哪些值算他的"](#v13插件只回答哪些值算他的)」。
>
> v1.4 (m18655) 改动:插件统一返 `Record<string,string>[]`(对象数组,一个插件可以同时给
> `id` / `name` / `value` 等任意多个字段),引擎按规则的 `column` 当 key 取值。
> 详见「[v1.4:插件返回对象数组](#v14插件返回对象数组)」。

> 详见「[v1.5:指定清单是自由编辑的 {key,value}[]](#v15指定清单是自由编辑的-keyvalue)」。

> 整条链上没有街镇 ⇒ 空集(失败关闭)。详见「[v1.6:内置 my_street](#v16内置-my_street我所在的街镇)」。
> v1.7 (m18652) 改动:内置插件从 5 个扩到 **7 个可选** —— 新增 `my_dept_only`(我的部门仅本级)、
> `my_sub_departments`(我的下级部门)、`my_street_tree`(我所在的街镇及以下);同时把恒返空集的
> `fixed` 从可选下拉里**藏起来**,只当引擎兜底。详见「[v1.7:再补三个内置插件](#v17再补三个内置插件m18652)」。

主键**不登记**,从 `information_schema.columns` 的 `column_key = PRI` 读
(`src/lib/data-scope-meta.ts`)。

**过滤发生在 SQL 里,不在内存里**:插件算出的是一串**值**(不是"逐行判断"),引擎把它编译成
`where 列 in (?, ?, …)`(`src/lib/data-scope.ts` 的 `valueList()`),由数据库筛行 ——
**没有任何"把整表拉回来再 for 一遍"的路径**。插件自己的开销也只有一次:内置插件走那条 30 秒缓存的
部门树(`loadDeptNodes()`),自定义插件通常是**一条** `ctx.query`;上下文(`buildPolicyCtx`)与
插件求值都是**每个请求一次**,不是每行一次。`previewScope()` 里那个 `select *` 是唯一例外,
只给预览弹窗取样张(`limit` 20),不在业务查询路径上。

### 主体(subject)

`*`(所有人) / `user:<用户 id>` / `role:<角色 id>` / `dept:<部门 id>`。
`dept:X` 的意思是"**X 部门的人**"(不是"X 部门这棵树"),它和 `user:X` 一样是"哪些人的请求命中这条规则"。
v0 的 `up:1`(往上第 N 级)已删除,`parseSubject()` 现在直接回 `null`。

## 内置插件(代码里写死,界面上只读)

| 标识 | 名字 | 语义 |
| --- | --- | --- |
| `self` | 我本人 | `[我自己]` |
| `my_departments` | 我的部门及以下 | 我所在部门 + 全部下级(**含自己**) |
| `my_dept_ancestors` | 我的部门及以上 | 我所在部门 + 全部上级(**含自己**) |
| `my_dept_only` | 我的部门(仅本级) | **只**我所在的那几个部门,不摊上级、不摊下级(v1.7) |
| `my_sub_departments` | 我的下级部门 | 我的部门及以下**减掉本级**;没下级 ⇒ 空(v1.7) |
| `my_street` | 我所在的街镇 | 往上找**第一个**街镇(闵行区 14 个街镇 / 工业区之一),只回它一个;非街镇 ⇒ 空 |
| `my_street_tree` | 我所在的街镇及以下 | 街镇本级 + 它下面**整棵子树**(v1.7);与 `my_street` 的差别就是多了子树 |
| `fixed` | 指定清单(兜底) | 恒返 `[]`,**不出现在可选下拉里**;留着只为不认识的自定义 key 兜底 |

内置插件是权限的地基,**不能改、不能删、也不能占用同名标识**(装载时内置优先,库里那条永远轮不到,
装载发现会 `logger.warn("data_scope.plugin_shadowed")`)。

「可选」与「已装」是两件事:`listPlugins()` 只吐非 `hidden` 的(现在是上表前 7 个,常量
`LISTED_BUILTIN_PLUGIN_KEYS`),而 `BUILTIN_PLUGIN_KEYS`(含 `fixed`)才用来**挡用户建同名插件**。
v2 之前 `fixed` 是可选的那一个,谁选中它谁就静默一行也看不到 —— v1.7 把它藏掉,消掉这个坑。

> v1.3 改:内置插件表砍掉了「产出」「值域」「绑定资源」三列(详见下文)。
> v2 (m20034) 改:用户**不再能写插件代码** —— 自建插件一律是「指定清单」(见
> 「[v2:输出值是插件属性](#v2输出值是插件属性规则不再带-items)」)。

## v1.3:插件只回答"哪些值算他的"

之前插件的形态是这样的:有一个 `produces` 字段(`value` / `row`)+ 一个 `domain` 字段(`user` /
`dept` / `town` / `area` / `text`)+ 一个 `resource` 字段(资源表名)。`produces` 决定编译成
`column in (...)` 还是 `主键 in (...)`,`domain` 决定输出值给什么人话名字,`resource` 决定
「给行」时取哪张表的主键。

m18228 的观点:这个分层多此一举 ——

1. **值域就是值域**,插件只回一串 id(`value`),没有「给行」那种形态;
2. **域归属由规则决定**:规则指定了**列**,列本身就是域(列是 `owner_id` ⇒ 域是 `user`,
   列是 `town_id` ⇒ 域是 `town`),查人话名字按规则列查就行,**不靠插件自报**;
3. 规则没指定列的 case 在 v1.3 不存在 —— `validatePolicyCombo({ column, pluginKey })`
   会拦下「选了 plugin 没选列」(m11388 时期的口径)。

落地的改动:

| 改的地方 | 之前 | 之后 |
| --- | --- | --- |
| `sys_data_plugin` 表 | 有 `domain` / `resource` / `code` 三列 | 只剩 `fn`(函数体) + 名字 / 标识 / 状态 / 备注 |
| `ResolvedPlugin` 类型 | `{ produces, domain, resource, fn }` | `{ fn }` —— 引擎不再查元数据 |
| `validatePolicyCombo` 入参 | `{ column, pluginKey, produces }` | `{ column, pluginKey }` |
| `compileRule` 形参 | `(rule, ctx, plugin)` | `(rule, ctx)` —— 插件一律「给值」 |
| `dataPlugin.test` 入参 | `pluginKey, params, column`(可选) | `pluginKey, params` —— **不查名字**(m18546) |
| `lookupLabels` 决策表 | 按 `plugin.produces + plugin.domain` | **已删**(m18546) —— 显示什么就是什么,不查 sys_user.name / sys_dept.name |
| 表单字段 | 「值域 / 绑定资源 / 形态」三块 | 只剩「函数体 / 名字 / 说明 / 状态」四块,**没有恰填一个的约束** |

### (历史 v1.3–v1.5)自定义插件只写一段函数体

> ⚠️ **v2 (m20034) 起这条路已封死**:用户自建插件不再有「函数体」字段,`sys_data_plugin.fn`
> 列已删,`new Function` 编译路径整体移除(`compileFn` / `makePluginCtx` / `PluginSdk` 都没了)。
> 下面这段只解释**内置插件在源码里长什么样**,供读 `src/lib/data-scope-plugins.ts` 时对照;
> 界面上只让填「输出值」清单。现役口径看「[v2:输出值是插件属性](#v2输出值是插件属性规则不再带-items)」。

内置插件的 `resolve` 是一段 async **函数体(JS,不是 TS)**。这些东西在作用域里直接可用:

| 名字 | 是什么 |
| --- | --- |
| `ctx.user` | `{ id, name }` 或 `null` |
| `ctx.roles` | `[{ id, name }]` —— 我身上全部角色 |
| `ctx.depts` | `[{ id, name, parentId, mine }]` —— 我所属部门 + 全部祖先(根在前);`mine: true` 才是我所属的,其余是上级 |
| `ctx.descendants` | `string[]` —— 我所在部门及以下的扁平 id 列表(**「我 + 子孙」**,不含上级) |
| ~~`params`~~ | **v2 已删** —— 规则行上不再有「插件参数」,`sys_data_policy.params` 列也掉了 |

**必填自己的 `return`,回一个对象数组**(`[{ id, name }]` / `[{ 任意 key: 任意字符串 }]` —— 引擎按规则的 `column` 取 `row[column]`)。内置插件在源码里的长相(同模块里还能用 `loadDeptNodes()` / `collectDescendantIds()` / `STREET_NAME_SET` / `ctxDeptIds(ctx)`):

```ts
// 1) 我本人(内置 self)
resolve: ({ ctx }) => Promise.resolve(ctx.user ? [{ value: ctx.user.id }] : []),

// 2) 我所在的部门 + 整棵子树(内置 my_departments)
resolve: async ({ ctx }) => {
    const roots = ctxDeptIds(ctx);                  // = ctx.depts.filter((d) => d.mine).map((d) => d.id)
    if (roots.length === 0) return [];
    const ids = collectDescendantIds(await loadDeptNodes(), roots);
    const byId = new Map((await loadDeptNodes()).map((n) => [n.id, n.name]));
    return ids.map((id) => ({ id, name: byId.get(id) ?? "" }));
},

// 3) 只有本级,不摊上级也不摊下级(内置 my_dept_only)
resolve: ({ ctx }) =>
    Promise.resolve(ctx.depts.filter((d) => d.mine).map((d) => ({ id: d.id, name: d.name }))),

// 4) 纯下级(内置 my_sub_departments):ctx.descendants 是「我 + 子孙」,减掉 mine 就是下级
resolve: async ({ ctx }) => {
    const mine = new Set(ctxDeptIds(ctx));
    if (mine.size === 0) return [];
    const byId = new Map((await loadDeptNodes()).map((n) => [n.id, n.name]));
    return ctx.descendants.filter((id) => !mine.has(id)).map((id) => ({ id, name: byId.get(id) ?? "" }));
},

// 5) 我这条链上的街镇(内置 my_street:往上找第一个名字落在名单里的祖先,只回它一个)
resolve: ({ ctx }) => {
    for (const dept of ctx.depts) {
        if (STREET_NAME_SET.has(dept.name)) {
            return Promise.resolve([{ id: dept.id, name: dept.name }]);
        }
    }
    return Promise.resolve([]);
},
```

两条常见需求就是这么配的(**插件 × 判据列**):

| 需求 | 主体 | 插件 | 判据列 |
| --- | --- | --- | --- |
| 七宝镇**队长**只看七宝镇的网格 | `role:<队长角色 id>` | `my_dept_ancestors`(给出整条祖先链) | `demo_grid.town_id` |
| 七宝镇**队员**只看自己管辖的网格 | `role:<队员角色 id>` | `self` | `demo_grid.owner_id` |

⚠️ **v2 起「不是沙箱」这条风险也没有了** —— 用户写的是纯数据(一份 `{key, value}` 清单),
服务端不再 `new Function` 执行任何用户输入,所以插件写接口也不再额外只给超管(m21097,
见下面「[权限点与菜单](#权限点与菜单)」)。

新增插件页现在只剩「标识 / 名字 / 输出值表格 / 说明 / 状态」,没有「恰填一个」的硬规则 —
**至少一行**即可(v1.5 的四个「抄个示例」按钮 + 样例上下文已随 v2 一起删)。

## v1.4:插件返回对象数组

之前(v1.3)的形状是 `string[]`:插件返一串字符串,引擎原样拼 `column in (...)`。问题是
`my_departments` 这种插件只能给一个字段 —— 想同时知道 id 和 name 时要么建两个插件
(`my_departments_id` / `my_departments_name`),要么加 `produces: "row"` 这个第二形态,
前端还要按 produces + domain 决定怎么渲染。插件数量膨胀,决策路径长。

m18655 的方案:**所有插件统一返 `Record<string,string>[]`(对象数组)**。

| 字段 | 之前(v1.3) | 之后(v1.4) |
| --- | --- | --- |
| `ResolvedPlugin.resolve` 返回 | `Promise<string[]>` | `Promise<Record<string,string>[]>` |
| `dataPlugin.test` 响应字段 | `values: string[]` | `rows: Record<string,string>[]` |
| 前端「输出值」段 | 一列原始字符串 | 一列原始对象(JSON.stringify 一行一个) |
| engine 取值方式 | 直接拼 `column in (values)` | 按规则 `column` 当 key 取 `row[column]`(兜底 `row.value`) |

### 引擎怎么从 row 里取值

```ts
for (const row of rows) {
  const valueKey = rule.valueKey?.trim() || column;  // ← v1.8 起,规则声明「值域的 key」优先
  const v = row[valueKey] ?? row.value;             // 再兜底 row.value(老 fixed 插件兼容)
  if (typeof v === "string" && v) values.push(v);
  else missingCount++;
}
```

两条兜底契约(均保留到 v1.8):

1. **`row[valueKey]` 优先**(v1.8 改:`valueKey` 留空 ⇒ 退回 column):规则声明了 `value_key='name'` 就取
   `row.name`,没声明就走老路 `row[column]`。同一个 `my_departments` 插件两条规则可各取 `id` / `name`。
2. **`row.value` 兜底**:`fixed` 这类"我只塞一组值,不管 column"的旧插件返
   `[{value: "七宝镇"}]`,column 怎么写都能取到 → 兼容已有规则。**v1.8 起新插件不应再写 `value` 这个字段**(等于「我给不出你列要的东西」的投降)。
3. **两条都没有**:`logger.warn("data_scope.plugin_column_missing", { ruleId, pluginKey, column, valueKey, missingRows, rowKeys })`,
   这条规则 `kind: "skip"`(规则当无效,不报"行也看不到",因为是配置错不是人没有)。

### 内置插件的新形状

| 插件 key | 返回 | 备注 |
| --- | --- | --- |
| `self` | `[{value: ctx.user.id}]` | 用户 id,value 兜底兼容 |
| `my_departments` | `[{id, name}, …]` | id + name;value 兜底不触发(有 id) |
| `my_dept_ancestors` | `[{id, name}, …]` | 直接用 `ctx.depts`(已带 name) |
| `my_dept_only` | `[{id, name}, …]` | **v1.7** 只 `mine` 的那几个,不摊上下级 |
| `my_sub_departments` | `[{id, name}, …]` | **v1.7** `ctx.descendants` 减掉 `mine`;空 ⇒ `[]` |
| `my_street` | `[{id, name}]` | 往上找第一个街镇,只回一个(m19644) |
| `my_street_tree` | `[{id, name}, …]` | **v1.7** 街镇 + 它下面整棵子树(比上面多个"及以下") |
| `fixed` | `[]`(恒空) | v2 起是**隐藏兜底**;用户填的清单走 `sys_data_plugin.output_values` |

> v1.7 (m18652) 补的三个插件 + `fixed` 转隐藏,见「[v1.7:再补三个内置插件](#v17再补三个内置插件m18652)」。

### 「七宝镇 / 街镇值」用例(m18652 + m19644 反馈)

`demo_grid.town` 存的是街镇**字符串值**(不是 id)。两条路都通:

- `my_departments` + column `town_id`(id 关联)→ 原 v1.3 用法,继续能用;
- **`my_street`**(内置,m19644 定稿)→ 从"我"所在的部门**往上找**,遇到的第一个名字落在
  「闵行区 14 个街镇 / 工业区」名单里的祖先就返它一个(`[{id, name}]`)—— column 填
  `town` 用 name、填 `town_id` 用 id,是同一个插件。整条链上没有街镇(例:线上那个
  「七宝镇队员」账号其实挂在 `区大数据中心 → 区数据局 → 区府` 下)⇒ 空集 ⇒ **失败关闭**。

> ⚠️ 一行里的 key 要**对得上列名** —— 引擎只按规则的 `column` 取 `row[column]`,取不到
> 就当这条规则没值(空集 ⇒ 一行也看不到)。

### migrate 行为变化

- **`fixed` 插件返的 row 现在带 `value` key**(之前是裸字符串)。`row.value` 兜底,
  已有规则无感。
- **自定义插件如果之前返 `{id: "..."}` 这种带 key 的对象**(v1.3 早期残留),
  现在直接生效 —— 引擎按 column 取即可。
- **响应字段改名 `values` → `rows`**,前端 + 测试 + 文档同步改。

## v1.5:指定清单是自由编辑的 {key,value}[]

v1.4 把插件返的 row 从字符串升成了对象 — 但「指定清单」(`fixed`)的入参还停留在 v1.3 的
"`string[]`,只能填一列值"。问题是:

- 规则 column 是 `town_id`(关联外键)时,你只能填 `["310112103", …]`(纯 id)
- 规则 column 是 `town`(名字)时,你只能填 `["七宝镇", …]`(纯名字)
- 想"同一个清单同时给 id 和 name" ⇒ 不行,v1.4 的引擎要每列一个插件

m18825 直接把规则的「输出值」从 `string[]` 升级成 `{key, value}[]` — key 完全自由
(`town_id` / `town` / 任意名字),value 跟着 key 走;`fixed` 插件逐行 `return { [it.key]: it.value }`,
完美契合 v1.4 的「插件返回对象数组」语义。

### 表单的样子

规则的编辑表单里,只有 `pluginKey = fixed` 才显示「输出值」表格区块:

| key(可自由命名) | value(可自由命名) |  |
| --- | --- | --- |
| `town_id` | `310112103` | 🗑 |
| `town` | `七宝镇` | 🗑 |
| ➕ 新增一行 | | |

- 行数上限 200 行,key 最长 64 字符,value 最长 256 字符(都有 zod 校验,超出直接 400)
- 整段存在 `sys_data_policy.params` 列里,**形态是 `JSON.stringify(items)`** — 不再是裸
  `string[]`(那是 v1.3 之前的形态,继续保留 `parseItems` 兜底兼容老数据)
- 「输出值」表格只对 `fixed` 启用;`self` / `my_departments` / `my_dept_ancestors` 这种"从
  上下文拿值"的插件不需要用户手填

### 整条链路闭合

| 段 | v1.3 | v1.4 | v1.5 |
| --- | --- | --- | --- |
| 规则存什么 | `params: string[]` | `params: string[]` | `params: JSON.stringify([{key, value}])` |
| 插件接收 | `args.params: string[]` | `args.params: string[]` | `args.items: RuleItem[]`(`params` 兜底) |
| 插件返什么 | `string[]` | `Record<string,string>[]` | `Record<string,string>[]`(无变化) |
| 引擎拼 SQL | `column in (...)` | `column in (...row[column])` | `column in (...row[column])`(无变化) |
| 前端渲染 | `<pre>` 一列字符串 | `<pre>` 一列 JSON 对象 | `<pre>` 一列 JSON 对象(无变化) |
| 表单控件 | `<textarea>` 多个字符串 | `<textarea>` 多个字符串 | 表格(key + value 双文本框 + 增删) |

### `fixed` 现在的样子

`src/lib/data-scope-plugins.ts`:

```ts
resolve: ({ items, params }) => {
    if (items && items.length > 0) {
        // v1.5 主路径:直接 return { [key]: value }
        return Promise.resolve(items.map((it) => ({ [it.key]: it.value })));
    }
    // v1.4 兜底:老 string[] 数据
    return Promise.resolve((params ?? []).slice(0, PLUGIN_PARAMS_MAX).map((v) => ({ value: v })));
}
```

### migrate 行为变化

- **新建规则的入参只接受 `items: RuleItem[]`**(`params: string[]` 不再被允许 — schema 砍了)
- **既有规则**:`params` 列如果存的是 v1.3 形态 `string[]`,`parseItems` 兜底 coerce 成
  `[{key:"value", value:str}]`,引擎照样能跑;但 **list 响应** 只会回 `items[]`(不再回
  `params`),前端展示按 items 来
- **行为不变**:`fixed` 拼出来的 row 仍是 `Record<string,string>[]`,引擎按 column 取值的
  链不变(`row[column]` 优先,`row.value` 兜底)
- **副作用可控**:`params` 列的 schema 改了(从 `string[]` JSON 升级成 `RuleItem[]` JSON),
  但因为持久层 `parseItems()` 兜底老形态,**不需要 ALTER**,也不需要数据迁移脚本

## v1.6:内置 my_street(我所在的街镇)

m18652 反馈「街镇值怎么配」时说好要加 `town_by_name` / `town_ancestor_names` 两个内置插件

`my_street` 的行为:

- 从 `ctx.depts` 里 `mine: true` 的那个部门**逐级往上走**(不是按数组顺序 `find`)——

> 「v1.6 my_street:14 个街镇名必须覆盖组织树里「镇、街道」下的每一个节点」就是拿**线上真实组织树**

## v1.7:再补三个内置插件(m18652)

m18652 反馈「值域插件再增加几个内置插件」。补的三个都只吃 `ctx`,不需要新表新列:

| 标识 | 名字 | 与已有插件的差别 |
| --- | --- | --- |
| `my_dept_only` | 我的部门(仅本级) | `my_departments` 是"本级 + 下级",这个是**只有本级** |

三个都遵守同一条失败关闭纪律:算不出东西就返 `[]`(编译成 `1 = 0`,一行也看不到),绝不返"全部"。

```ts
// my_dept_only —— 只 mine 的那几个,不摊上级、不摊下级
resolve: ({ ctx }) =>
    Promise.resolve(ctx.depts.filter((d) => d.mine).map((d) => ({ id: d.id, name: d.name }))),

// my_sub_departments —— ctx.descendants 是「我 + 子孙」,减掉 mine 就是纯下级
resolve: async ({ ctx }) => {
    const mine = new Set(ctxDeptIds(ctx));
    if (mine.size === 0) return [];
    const byId = new Map((await loadDeptNodes()).map((n) => [n.id, n.name]));
    return ctx.descendants.filter((id) => !mine.has(id)).map((id) => ({ id, name: byId.get(id) ?? "" }));
},

// my_street_tree —— 先按 my_street 的办法找街镇,再取它下面整棵子树
resolve: async ({ ctx }) => {
    const street = ctx.depts.find((d) => STREET_NAME_SET.has(d.name));
    if (!street) return [];
    const nodes = await loadDeptNodes();
    const byId = new Map(nodes.map((n) => [n.id, n.name]));
    return collectDescendantIds(nodes, [street.id]).map((id) => ({ id, name: byId.get(id) ?? "" }));
},
```

## v1.8:规则声明「值域的 key」(m23422)

v1.4 把插件输出升级成 `Record<string,string>[]`(`{id, name}, …`),v1.5 把"指定清单"也升级成
`{key, value}[]`,但**引擎取哪个字段**一直是写死的"用 `row[column]` 兜底 `row.value`"。问题是:

- 同一个插件要支持**多条规则**:`my_departments` 既能给「我看 id」(配 `column=town_id`),
  又能给「我看 name」(配 `column=town_name`)—— 一条清单复用到两条规则,而不是建两个插件;
- 同一个清单里**两类值并存**:登记 `{key:"town_key", value:"七宝镇"}` 和 `{key:"group_key", value:"…"}`,
  两条规则各取各的 key,互不干扰;
- 之前那条兜底 `row.value`（v1.4 给"我只塞一组值"的旧插件用的）这次正式退役 —— 现在清单插件
  的每一行都得有一个**真实存在的 key**,否则失败关闭。

m23422 把这条契约显式化:**规则侧**多一列「值域的 key」(`sys_data_policy.value_key`),
**插件侧**多一个**声明**「我能给的 key 集合」(`ResolvedPlugin.valueKeys: string[]`)。

### 字段的形态

| 侧 | 字段 | 含义 |
| --- | --- | --- |
| 插件 | `ResolvedPlugin.valueKeys: string[]`(必填) | 引擎能从一个 row 里取到的所有 key。界面拿它渲染下拉,写明「诚实反映 `resolve()` 会给的 key」 |
| 规则 | `sys_data_policy.value_key: varchar(64)` nullable | 选哪一个 key 去和上面的列比;**留空 = 老规则,按 column 推断** |
| 内置 | 每个内置条目都硬写一份(见下) | `self` → `["value"]`,街镇/部门族 → `["id","name"]`,`fixed` → `[]` |

### 引擎怎么从 row 里取值

```ts
const valueKey = rule.valueKey?.trim() || column;   // 留空就退回老规则
const v = row[valueKey] ?? row.value;              // 优先 valueKey,没有再兜底 row.value(老 fixed 兼容)
if (typeof v === "string" && v) values.push(v);
else missingCount++;
```

`row.value` 兜底保留(老数据 / 老插件兼容);新插件**不**应该写 `value` 这个字段 —— 写它等于自暴自弃
「我给不出你列要的东西」。

### 内置插件的新形状(增量)

| 插件 key | valueKeys | 备注 |
| --- | --- | --- |
| `self` | `["value"]` | 返 `[{value: ctx.user.id}]` |
| `my_departments` / `my_dept_ancestors` / `my_dept_only` / `my_sub_departments` / `my_street` / `my_street_tree` | `["id", "name"]` | 同一插件两条规则可各取 `id` 或 `name`,互不干扰 |
| `fixed` | `[]` | 不让用户直接用;它能给的 key 是 [];`toPlugin()` 从用户的 `output_values` 里去重派生 |

### UI 上多了一列

数据范围规则的「**判据列**」后面跟一列「**值域的 key**」(`settings-data-scope-form.tsx` 的新 DetailRow,只在选了插件且插件有 `valueKeys` 时显示),下拉内容是当前选中插件的 `valueKeys`;选了一个 key 才有意义,不选 ⇒
提交校验拦下「这个插件给的是值,还得选一个 key」。

`checkRule`(router)对**写入端**也兜一层:插件存在 + valueKeys 非空 + 用户写的 valueKey 不在里面 ⇒ `BAD_REQUEST`,消息是「插件「{label}」不给这个 key:{valueKey}。它现在能给:{a} / {b}」—— 表单下拉都不会出现这个 key,这条兜底是给"库里改坏"的笔录补档。

### 失败关闭

1. **键不存在**:`row[valueKey]` undefined + `row.value` undefined ⇒ `missingCount++`,values 空 ⇒ `kind: "skip"`,规则这条记成 `skipped`(不再悄悄全放行)。
2. **键给错**:路由器在写入时直接拒(见上),免得「建出来就永远看不到任何行」。
3. **键过时**:库里先建好(`value_key='town_key'`),后来插件改版 `valueKeys` 不再含 `town_key` ⇒
   引擎照样失败关闭(测试 `tests/data-scope.test.ts` 的「值域的 key:同一个清单放多类值」用例 ④ 用 `db.update` 直接改坏验证)。

> 兼容老规则:`value_key` 为空(没填)⇒ 引擎退回 v1.4 的 "按 column 推断" 路径,与历史行为一致;
> 老库里的 `sys_data_policy.value_key` 一律是 `NULL`,新建/编辑才填 —— **不需要 backfill**。

### 表 / DDL

新增 `sys_data_policy.value_key varchar(64) null`,已加进 `scripts/create-system-tables.ts` 的 `COLUMN_UPGRADES` 与 `scripts/create-better-auth-tables-dm.ts` 的 `columnUpgrades`,`pnpm db:create` 自动补列。`scripts/sync-table-meta.ts` 同步了列注释。

| 一条上线规则都没有 | **不过滤**(「空表 = 能力没开」,新装系统不会突然全看不见) |
| 有规则,但没一条命中我 | `1 = 0`,一行也看不到 |
| 命中了,但插件算不出值(比如我没部门) | `1 = 0`(**v0 就是在这里放行的,实测 71/71 可见**) |
| 规则引用的插件坏了 / 被停用 | 忽略这条 + `logger.warn("data_scope.rule_broken")`,绝不 500 |
| 多条规则同时命中 | 取**并集**(`or`) |

### 怎么给一张表接上过滤

1. 在 `src/lib/rbac.ts` 的 `DATA_SCOPE_BY_PATH` 里登记:`"demoGrid.list": { resource: "demo_grid" }`
   —— **不登记 / 不写进 `UNSCOPED_QUERIES`,读接口守卫(`tests/auth.test.ts`)会红**。
2. resolver 里显式筛:

   ```ts
   const scope = await ctx.scope();                          // 资源按 path 从 DATA_SCOPE_BY_PATH 查
   return db.select().from(sysDemoGrid).where(and(scope));    // 没配规则 ⇒ undefined,`and()` 自动扔掉
   ```

   `ctx.scope()` 不传参就按当前接口的 path 查资源;要筛别的表才传表名(`ctx.scope("demo_grid")`,
   **传的是字符串,不是 drizzle 表对象**)。没登记的接口调它会**抛错**,不会静默不筛。

3. 没有合适的插件,再去 `/settings/data-plugins` 加插件。

**显式 `ctx.scope()` 是刻意的**:它让"谁忘了加"可以被 review 出来(对比之下 `AsyncLocalStorage`
是隐形的,漏了就永远查不出来)。

## 新建 → 试算 → 上线(状态的三个值)

规则写下来**不是立刻生效**。`sys_data_policy.status` 三态(常量在 `src/lib/data-scope-spec.ts` 的
`POLICY_STATUS`):**「启用」是配置层面的开关,「上线」才是真正进引擎**(m23000 之前这两个标签叫反了)。

| 值 | 界面叫 | 引擎 | 这一行能做什么 |
| --- | --- | --- | --- |
| `2` | **启用** | **不加载**(`loadRules()` 只读 `status = 1`,即 `POLICY_STATUS.live`) | 预览 · 上线 · 编辑 · 删除 |
| `1` | **上线** | 加载,参与筛行 | 预览 · 停用 · 编辑 · 删除 |
| `0` | **停用** | 不加载 | 预览 · 启用 · 编辑 · 删除 |

- **新增 / 改过形态的规则一律落 `2`**(启用):值域是弱类型(列是字符串、插件回 id),配错了不报错、
  只会一行都命中不到 —— 所以「先预览,再上线」是硬流程,而不是靠人自觉。
- **改「形态」会自动退回 `2`**:`dataScope.update` 逐字段比对 `subject / resource / column /
  plugin_key`,只要有一个值真的变了、而调用方又没显式给 `status`,就落回「启用」并回
  `demoted: true`(界面上是琥珀色提示)。只改 `remark` 不动状态。显式给的 `status` 优先级最高。
- 写规则的人**不必**伸手改状态:点行内「预览」算得过去,再点「上线」;
  台账行内也有「启用 / 上线 / 停用」三个动作(都走 `update`,所以权限点仍是 `sys:scope:edit`,
  没有为此新增 procedure、权限点或菜单)。

## 行内「预览」(只读试算)

入口在规则台账每一行的操作列(弹窗组件 `src/components/modules/settings/settings-data-scope-preview-dialog.tsx`),
接口 `dataScope.trial`(只读 query)。

为什么每条规则旁边都要留一个试算口:数据权限改的是"别人能看见哪些行",配错的方向恰好是**多看见**;
而值域是弱类型,一条写错的规则在真跑之前看不出任何异常。**版面按"先看数据、再看依据"排**(m23214 重做):

1. **结论带** —— 一个大数字「可见 N / 共 T 行」,旁边跟着「现在 N 行 → 上线后 M 行(这条规则多 / 少放行几行)」;
   基线按库里**当前上线**的规则算(不带 `ruleId`),试算把**这一条**当成上线规则一起算(带 `ruleId`),
   差额就是这条规则的作用;已经把这条上线的规则再算一次也是安全的(引擎按 id 去重);
2. **数据判断依据** —— 判据(这条规则长什么样:`列 ∈ 插件(我)` / 整类可见)+ 按谁算(人话名 · 角色 · 部门链)
   + 这条规则对**这个人**算出来的账(`整类可见` / `按值筛行` / `取不到值 ⇒ 一行看不到` /
   `插件不可用 ⇒ 一行看不到` / `与这个人无关`);
3. **SQL(引擎真跑的)** —— `previewScope()` 用**同一个** dialect 把**同一个**语句对象渲染成「文本 + `?` 参数」
   (`type ScopeSql = { text, params }`):上面那条数行数、下面那条取样张,两段都贴出来。
   **不另写一份人话描述充当"SQL"** —— 那种描述迟早跟真 SQL 漂移;达梦线上万一渲染不出来就少这一块,试算照常;
4. **引擎放行的真实数据(主区,占满剩余高度)** —— `select *` 出来的真行,表头粘住、可横竖滚动,只读;
   **一行都没放行时不写一句"没有数据"**,整块换成「**断在哪一步**」的原因清单(表本身空 / 主体不含这个人 /
   值域取不到值 / 值取到了但没有一行命中那一列 / 计数过了但样张取样失败)—— 全部来自引擎回的账,不猜;

(数据判断依据里已经把"按谁算"的人话名 + 角色 + 部门链都摊开了 —— m23422 把弹窗里那条独立的
「可展开的次要证据」折叠掉,等效条件与上下文卡片不放这儿。)

弹窗里还有一块**上下文卡片**,把"按谁算"的两段部门摊开看 —— 取不到值时一眼分得清
是「这人没部门」还是「规则没命中他」。后端已经在 `policyCtx.depts[i]` 上把"我所属"那段标好
(`mine: true`,叶节点;其余是祖先链),前端只管渲染。**字段命名口径**(m18035):
后端响应字段已经从 `depts[]` / `descendants[]` 改名为 `ancestors[]` / `children[]`,跟 UI 标签「部门祖先」/「部门children」一一对齐;
**底层数据模型** `ctx.depts` / `ctx.descendants` 没动(改它们牵动引擎 + 插件代码,得不偿失),只在「给 UI 看」这一步换名字。

| 行 | 内容 |
| --- | --- |
| 考生 | 头像 + 「我本人」徽标 + 人话名(库里查不到时退化成 id,见 `data-scope.ts:171`);接口支持换人,界面一律按当前登录人算 |
| 角色 | `[队员]` 这样的徽标列表,空就显示 — |
| 部门祖先 | 根 → 我(含 mine 那段);`mine=true` 用琥珀色徽标 + 「我所属」后缀,其余用淡色文字串起来;空 = 显示 — |
| 部门children | 我 + 子孙(扁平,去重);`mine=true` 用琥珀色徽标 + 「我所属」后缀,子孙用紫色徽标;空 = 显示 — |

「部门祖先」是把"祖先链"和"我"叠在一起画 —— 后端已经排好序、根在前,前端不再爬树。

**「部门children」** 是后端在 `buildPolicyCtx` 里 **预先算好**的扁平列表(`ctx.descendants: string[]`)——
只装 id,不装名字(父组件按需查 `sys_dept.name`)。这一步在装配层做,不是写死**"必须显示**子树"—— 装好后**同时**给「部门祖先」「部门children」两段,
插件作者(`ctx.descendants`)与 UI(`ctx.descendants`)读的是同一份值。

⚠️ **「部门祖先」是"祖先 + 我",不含子树**。子树是插件的活(`my_departments` / `my_dept_only` / `my_street_tree`,都读 `ctx.descendants`),
所以规则语义能写成「我的部门及以下」这种可配的选择,而不是装配层的一个开关。

值域插件预览弹窗(`/settings/data-plugins` ▸ 某行 ▸ 「预览值域」)也是同一份上下文 —— 但**一律按当前登录人算**;
想换人就用系统的"切换身份"功能,这里不另开通道。后端 `dataPlugin.test` 回 `{ userName, isMe: true, roles, ancestors[], children[], rows[] }`,
**字段名已统一**(原来是 `depts[]` / `descendants[]` / `values[]`,m18035 改 `ancestors[]` / `children[]`,
v1.4 m18655 改 `values[]` → `rows[]` —— 插件返对象数组,UI 标签「部门祖先」/「部门children」/「输出值(原始对象)」一一对齐)。
配合前端弹窗里的两段:当前上下文(谁)/ 输出值(插件取到的)。(v2 前的第三段「参数(给插件的输入)」
已随 `testParams` Textarea 一起删 —— 插件不再接受调用方传参。)
值域插件预览弹窗共用 `src/components/modules/shared/policy-context-block.tsx`(数据范围行内「预览」弹窗 m23422 起不再用它 —— 那块按"数据判断依据"那一格已经把人话名 + 角色 + 部门链都摊开了)。

「输出值」段 **一列原始对象**渲染(v1.4 m18655 起改):`rows[]` 里有什么对象就原样 JSON.stringify 贴出来,每行一个(`<pre>` 等宽字体,长截断 hover 全文)。要瞄具体字段看 JSON。
**不查名字**(m18546) —— 显示什么就是什么。理由:

1. (历史论据,当时插件还能写 JS)插件代码是任意 JS(`new Function` 不是沙箱),插件自报的"域"不可信 —— 拿它去决定查 sys_user 还是 sys_dept 是不安全的决策路径。
2. 即使按调用方的 `column` 查,也只是把决策从后端挪到前端,治标不治本;且 user 明确要"显示什么就是什么"。
3. 需要"看名字"的场景是另一种预览模式(单独查),不是插件试算的活。

> m18546 之前的口径(v1.3 早期):按 `column` 查 `sys_user.name` / `sys_dept.name`,查不到回 `null`。已删 —— `lookupLabels` 函数、`valueLabels` 字段、`column` 入参全删(详见 `src/integrations/trpc/routers/data-plugin.ts` 的「m18546」注释)。
>
> v1.4 (m18655) 之前的口径(v1.3):插件返 `string[]`,引擎直接拼成 `column in (...)`。插件没法同时表达"我有 id 也有 name" —— `my_departments` 只能选一个字段。已删 —— 改为 `rows: Record<string,string>[]`,引擎按规则 column 取 `row[column]`(兜底 `row.value`),详见「[v1.4:插件返回对象数组](#v14插件返回对象数组)」。

每次试算都给三样东西:

| 产出 | 回答的问题 |
| --- | --- |
| 等效条件 | 引擎真编译出来的那个 `where`(「不筛行」= 对这个人全可见) |
| 规则的账 | 这张表每条参与计算的规则对**这个人**分别算什么:`整类可见` / `按值筛行` / `取不到值 ⇒ 一行看不到` / `插件不可用 ⇒ 一行看不到(不是放行)` / `与这个人无关` |
| 真实样张 | `select *` 出来的真行(只读;取不到就把原因写进 warning,不 500) |

⚠️ **「可看到 0 行」有两种截然不同的原因**:这个人一个值都没取到(比如没有部门),或者规则
压根没命中他 —— 只有把「规则的账」摊开才分得清。这正是 v0 那套 fail-open 留下的教训。
试算的主体不含这个人时,`warning` 会直接说「这条规则对 TA 不起作用,加了也不多看见行」。

实测注意:`demo_grid` 的 `owner_id` 只有 **39/71** 行有值,用「我本人」当插件试最多看到 39 行,
是数据没回填,不是引擎算错。

## 缓存

规则 / 插件 / 部门树 / 资源元数据各 30s TTL(`PLUGIN_TIMEOUT_MS = 3000` 是插件执行上限)。
**任何写操作之后必须清缓存**,否则 30s 内界面看到的还是旧条件:

```
clearDataScopeCache()   规则变了
clearPluginCache()      插件变了
clearDeptCache()        部门树变了
```

只有一个缓存**没有**清除函数:资源元数据(`loadResourceMeta`,TTL 30s)。因为它的失效条件是
「表结构变了」,而那件事只可能由 `scripts/` 里的建表脚本在外带 DDL 完成 —— 进程内没有清它的
时机,也没人调用过。**跑完 `pnpm db:create` 之后最多等 30s** 资源下拉才会看到新表 / 新列。
