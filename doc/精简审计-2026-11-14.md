## 一、DB:字段必要性

### P0-1 `sys_menu.status` 是死列 —— 唯一一处「谁都不读」

- 定义:`src/db/data-base-schema.ts:110`,DDL `scripts/create-system-tables.ts:43`。
- 证据:`routers/menu.ts` 的 `toMenu()` 不投影它、`update`/`create` 不写它、列表不过滤它。
  全仓(`src` / `scripts` / `tests`)对它只有 schema 自身的定义与注释。schema 注释自己也承认
  「当前没有任何代码读它」。
- 结论:要么**删列**(schema + MySQL DDL + 达梦 DDL + `sync-table-meta.ts` 四处),要么**接进菜单页**
  当「启用 / 停用」并明确 `visible` 与它的分工。当前状态是「存了一列、没人管」,属于最容易出
  「运维改了这一列却什么也没发生」的地方。**建议删**——`visible` 已经承担上下线语义。
  连带:DDL 里要加一条 `COLUMN_DROPS`(老库删列),否则老库留着孤儿列。

### P0-2 `tc_task` 的索引与真实查询不匹配

- 列表查询(`routers/task-query.ts:265-350`)的实际形态:
  `deleted_at IS NULL` + 可选 `status` / `workflow_id` / `created_after` / `created_before`,
  `ORDER BY created_at DESC, id DESC`。
- 现有索引:`idx_task_status_created(status)`(`data-base-schema.ts:967`,三处 DDL 同步)。
  ①名字承诺 `(status, created_at)`,实际只有单列 `status`;②`workflow_id` 是筛选列却**没有索引**;
  ③`ORDER BY created_at` 没有任何索引可走,列表页在数据量上来后必然排序全表。
- 建议:改成 `index("idx_task_status_created").on(table.status, table.created_at)`,
  再加 `index("idx_task_workflow").on(table.workflow_id)`。改名要在 DDL / 达梦脚本 / meta 三处同步
  (达梦是 `create index if not exists`,MySQL 要走 `COLUMN_UPGRADES` 之外的改名段)。

### P1-3 `sys_notification_delivery.provider` / `.last_error` 与 attempt 表重复

- `lib/notification-delivery.ts:120-145`:同一事务里,`delivery` 行写 `provider / provider_message_id /
  sent_at / last_error`,`attempt` 行写 `status / provider / error / started_at / finished_at`。
- `provider` 与 `last_error` 两边**值完全相同**(同一个 `provider?.name`、同一个 `error` 字符串),
  attempt 行还多存了历史(`attempt_no`)。所以 delivery 侧这两列是「最新一条 attempt 的拷贝」。
- 建议:delivery 只留「当前状态」(`status / attempts / next_attempt_at / locked_until / lock_token /
  provider_message_id / sent_at`),`provider` 与 `last_error` 从「最新 attempt」派生。
  代价:读失败原因要多一次 join 或子查询。如果只在一处展示,建议**保留 delivery 侧、删 attempt 侧的
  `provider`/`error`**(attempt 只留 `attempt_no / started_at / finished_at` 作为时间轴)——更省事。

### P1-4 三张「只增不改」的表带 `updated_at`,永远等于 `created_at`

- `sys_tag_relation.updated_at`(`:264`)、`sys_user_dept.updated_at`(`:529`)、
  `sys_casbin_rule.updated_at`(`:572`)。
- 证据:全仓没有任何 `update(sysTagRelation| sysUserDept | sysCasbinRule)` 调用 —— 这三张表只 insert / delete。
- 结论:这三列是纯冗余(写入即等于 created_at)。删掉能少三列、少三次写入。
  `sys_casbin_rule` 要留意:`created_at/updated_at` 是通用审计列,若将来策略行要改(例如加有效期),
  留着也有用。**建议:前两张删,casbin 那张留**(它在权限热路径上,留着将来省一次迁移)。

### P1-5 `sys_para.id` 是无意义代理键,还被渲染到界面上

- 表的主键是 `para_key`(`:176`),`id` 只是一个 not null 的 nanoid(`:175`),每次写都 `newId()`。
- 界面还把它显示出来:`settings-parameters-detail.tsx:53` `<span className="font-mono text-xs">{row.id}</span>`。
- 结论:这一列对用户没有任何信息量(「库里的无意义短串」,连 `parameters-table.tsx:11` 的注释都这么写)。
  **建议删列 + 删掉详情里那一行**,或者把它改成有业务含义的东西(如「参数说明/来源」)。

### P1-6 better-auth 四表里有一批永远为空的列

- `sys_session.ip_address` / `user_agent`(`:314-315`):全仓无引用(BA 的 session 镜像不写)。
- `sys_account.access_token` / `refresh_token` / `id_token` / `access_token_expires_at` /
  `refresh_token_expires_at`(`:339-344`):模板只启用 `credential`(邮箱 + 密码)登录,没有社交登录 provider。
- 这两张表由 Better Auth 的 adapter 驱动,列名/模型名不能改(AGENTS 明确写了),所以**不能直接删**。
  建议:**在文档里标注「本模板未启用 OAuth / 访客设备留痕,这些列恒为 null」**,避免后来者以为在用。
  (删列的风险:BA 升级后 adapter 需要这些列。)

### P2-7 「模板单版本」与「任务保存快照」互相打架(设计问题,不是冗余)

- 模板编辑:`routers/task-report.ts:218-223` 只覆盖 `tc_report_template.payload`;
  已绑定任务的结构写在 `tc_task.report.schema`(`:316`),**不会跟着变**。流程模板同理(`tc_task.workflow`)。
- 于是「模板是单版本、编辑即覆盖」与「任务持有结构快照」两条规则叠在一起的实际效果是:
  **改模板对存量任务无效**,而且界面不提示。用户会报「我改了模板,老任务里还是老表头」。
- 建议(二选一,写进 `doc/task-close.md`):
  a. 模板改动时**批量刷新**未开始任务的快照(有填报数据的任务不动);
  b. 放弃快照,任务只存 `reportId`,读的时候现取模板(但那样模板改动会破坏历史填报的行结构 ——
  所以 a 更安全)。
- 顺带:同一份 schema 现在最多存三处(模板 `payload` / 任务 `report.schema` / 填报行 `draft`),
  a 方案下「模板 payload」仍是唯一真源,快照只是派生副本 —— **这是可接受的冗余**,别再往回删。

### P2-8 遗留列清理已就位(确认,无需动作)

- 老库里的 `sys_user_dept.role_id` / `sys_data_policy.params` /
  `sys_data_plugin.produces·impl_kind·decl·domain·resource·fn` / `tc_member.is_primary`
  **在新建表的 DDL 里已经没有了**,只在 `COLUMN_DROPS`(老库删列)与达梦脚本里作为历史兼容出现。
  新装环境是干净的 —— 这一点没问题,不用动。

### P2-9 结构性成本:一张表的形状要同步四处

`src/db/data-base-schema.ts` + `scripts/create-system-tables.ts`(MySQL)+ `scripts/create-better-auth-tables-dm.ts`(达梦)
+ `scripts/sync-table-meta.ts`(列注释 / 索引名真源)。本次审计我用脚本比对过,**当前四者是一致的**
(schema 与 DDL 无孤儿列、无缺列;达梦是 camelCase↔snake_case 的正常映射)。
但「改一列要动四个文件」是这个模板最大的重复来源。
**建议加一条 `pnpm db:check`(只读 diff)**:解析 schema 的列 → 比对 MySQL DDL + 达梦 DDL + meta 注释,
不一致就报错并给出 ALTER 建议。这条脚本我已在本机用一次性脚本验证过逻辑可行(解析 34 张表 / 318 列)。

## 二、前端

### P0-1 `settings/` 57 个文件平铺在一个目录里

`src/components/modules/settings/` 一层平铺 57 个文件(10119 行),命名全是 `settings-xxx-{page,table,form,detail,excel}`。
**问题不是行数,是「一个实体 = 4~5 个文件」这个约定在大目录里已经失控**(57 个文件里要靠前缀排序才能找到东西)。
**建议:按实体分目录**,例如

```
settings/
  users/{page,table,form,detail,excel}.tsx
  roles/{…}
  dictionary/{…}
```

import 路径会变(`#/components/modules/settings/users/page`),但**文件名可以不变**,改动是纯机械的、
git mv + 改 import,风险低。收益:目录一眼看得出有几个实体、每个实体下有几个视图,新增实体不用再想命名。

### P0-2 `task-detail-page.tsx` 1246 行,主体是一个 1060 行的组件

同文件尾部还有 `PeopleRow` / `REJECT_PRESETS` / `APPROVE_PRESETS` / `ROLE_LABEL` / `ROLE_WHY` 等散落件。
**建议拆成 4~5 个同目录组件**:头部+操作条 / 流转条(`task-flow-spine.tsx` 已在) / 成员区 / 评论+催办 / 填报。
注意 `REJECT_PRESETS` / `APPROVE_PRESETS` / `ROLE_LABEL` 这类**文案与业务常量应该搬到 `src/lib/task-close-spec.ts`** ——
现在写在组件文件里,后端 `lib/task-close-spec.ts` 已经有一套状态/优先级常量,两边口径会漂。

### P1-3 `shared/filter-chips.tsx` 207 行只有画廊一个调用方
