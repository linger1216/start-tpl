## 数据库

**两张 schema 文件口径不同,不要混:**

| 文件 | 管辖 | 迁移 |
| --- | --- | --- |
| `src/db/schema.ts` | 只剩 `todos` 示例表 | 由 drizzle 迁移管理(`drizzle/`) |
| `src/db/data-base-schema.ts` | **27 张表**:系统设置五张(`sys_menu` / `sys_dict` / `sys_para` / `sys_tag` / `sys_tag_relation`)+ **认证六张**(`sys_user` / `sys_session` / `sys_account` / `sys_verification` + `sys_account_lockout` 登录风控 / `sys_rate_limit` 限流,见 §三)+ **权限四张**(`sys_dept` / `sys_role` / `sys_user_dept` / `sys_casbin_rule`,见「认证 ▸ 权限模型」)+ **数据权限两张**(`sys_data_policy` / `sys_data_plugin`)+ `sys_notice` / `sys_log` / `sys_file` / 示例表 `demo_grid` + 任务闭环六张 `tc_*` | **不进迁移**:只声明"读写的形状",DDL 由 `scripts/create-system-tables.ts`(`pnpm db:create`)**和** `scripts/create-better-auth-tables-dm.ts`(达梦)维护。**改列之后要同时改它 + 这两个脚本** |

**不要把 `data-base-schema.ts` 的表并进 `schema.ts`** —— 下次 `db:generate` 会生成 `CREATE TABLE`,而库里已存在 → `db:migrate` 直接 1050 报错。

- 连接在 `src/db/index.ts`,用 `drizzle-orm/mysql2`,导出 `db`
- 迁移配置在 `drizzle.config.ts`:dialect `mysql`,输出 `./drizzle`,`schema` **只指向** `./src/db/schema.ts`,读 `.env.local` → `.env`
- env 流转:`.env.example`(随模板分发,无凭据)→ `cp .env.example .env.local`(本地填写,已 gitignore)
- `DATABASE_URL` **缺失会直接抛错**,`src/db/index.ts` 与 `drizzle.config.ts` 都有显式检查
- 改 schema 后:`pnpm db:push`(开发期)或 `pnpm db:generate && pnpm db:migrate`
- 建表:`pnpm db:create`(27 张表 = 20 张 sys_* + demo_grid + 6 张 tc_* = 设置五 + 认证四 + 权限四 + 数据权限二 + 通知 / 日志 / 文件 / 示例表 + 账号锁定 / 限流,幂等 `create table if not exists`,不 drop 不 seed)。**给已存在的表加列**要登记在脚本的 `COLUMN_UPGRADES` 里(`create table if not exists` 不会补列);**删列**登记在 `COLUMN_DROPS`(列被合并 / 废弃时用 —— 不注销旧列,老库里那列还带着 not null,下一次插入就会违反约束);**改旧列的型**登记在 `COLUMN_TYPE_FIXES`(老库里列型与声明漂移时用,如 `sys_dict.items` 的 `text → json`,已是目标型则跳过);**改表名**登记在 `TABLE_RENAMES`(达梦侧改完会自动清一次计划缓存)
- 种子:`pnpm db:seed:menus`(把 `NAV_NODES` 写进 `sys_menu`)、`db:seed:dicts`、`db:seed:paras`、`db:seed:tags`、**`db:seed:rbac`(权限演示数据)**、`db:seed:demo`(通知 + 网格演示数据)—— 六个都幂等"只补不覆盖"
- 老库换主键:`pnpm db:migrate:ids`(语义 id → nanoid + 补 `sys_dict.code` + 修 `para_type` 与值不匹配的行;幂等)
- 表注释 / 列注释 / 索引名:`pnpm db:sync:meta`(表名改过之后注释不会跟着变,会留下"描述旧列名"的残留 —— 那比没注释更误导)。
  **注释的唯一真源是 `scripts/sync-table-meta.ts`**(表注释 + 列注释两张清单),**别往建表脚本的 CREATE 里塞注释**;`pnpm db:create` 建完表会自动调它一次。
  MySQL 没有 `comment on` 语法,改注释只能 `alter table … modify column …` 把**列定义整条重写**;达梦走 `comment on table/column`(不用重写定义)。详见「已知陷阱 ▸ MySQL 改注释」
- `db` 只能在服务端用(tRPC procedure、server function)。不要从客户端组件 import

### 软删除(统一口径)

业务表删行**不再物理删**,统一写 `deleted_at`(UTC,`NULL` = 还活着;`sys_file` 除外 —— 它已有 `status = 2` 的行级软删)。
口径、理由与 API 集中在 `src/lib/soft-delete.ts`,**一处定义、各域照抄**:

| 件 | 说明 |
| --- | --- |
| 列 | `deleted_at datetime NULL`,加在 10 张业务表:`sys_menu` / `sys_dict` / `sys_para` / `sys_tag` / `sys_user` / `sys_dept` / `sys_role` / `demo_grid` / `sys_data_policy` / `sys_data_plugin` |
| 读 | 一律带 `alive(table)`(`= isNull(deleted_at)`):列表 / 详情 / 下拉 / 树 / 计数 / 导出 / 鉴权 / 数据范围引擎 / 权限引擎都算"读",漏一处就把已删行暴露给用户 |
| 删 | `db.update(表).set(softDeleted())`;带**唯一业务键**的表再把键换成 `tombstone(原值, id, 列宽)` |
| 还原口 | 想恢复就把墓碑后缀去掉:`fromTombstone(key)`(`src/lib/soft-delete.ts` 的纯函数,**有损** —— 列不够宽时原值尾部在写入那一刻就被截掉了);要查「谁被删过」直接看 `deleted_at` 非空的行 |
| 唯一键让位 | `sys_user.email` / `sys_role.name` / `sys_dict.code` / `sys_menu.path` / `sys_para.para_key` / `sys_data_plugin.plugin_key` 上有唯一索引。软删时把键改成 `<原值前缀>#d#<id 尾段>`,否则"删掉「测试角色」之后再也建不出同名角色",而且界面看不到那条占位的死行 |
| 不加这一列 | 纯关联表(`sys_tag_relation` / `sys_user_dept`)与运维表(会话 / 账号 / 令牌 / 日志 / 限流 / 锁定)—— 要么跟主行一起重放,要么本身就是流水 |
| 用户这条特别 | 软删 `sys_user` 仍**硬删** `sys_session` / `sys_account` / `sys_user_dept` 与 casbin 的 `g` 行,并且**邮箱必须让位**:Better Auth 的 adapter 不认识 `deleted_at`(只按邮箱查),不让位就等于已删账号还能登录 |

**不要**改用「唯一索引 + `deleted_at` 列」那种写法:MySQL 的唯一索引把 `NULL` 当互不相等,唯一性直接失效(实测同一个 `code` 能插进三行)。
**`pnpm db:create` 也改不了唯一索引的列**:`scripts/sync-table-meta.ts` 比索引名、不看列 —— 所以只能靠墓碑让位,别指望加一列就能改键。

### 认证(Better Auth)

**整个后台 `(main)` 都要登录**,登录页在 `/login`(故意放在 `src/routes/` 根下 —— 没有后台外壳)。

| 件 | 位置 | 说明 |
| --- | --- | --- |
| 服务端实例 | `src/lib/auth.ts` | `drizzleAdapter(db, { provider: "mysql", schema: { user: sysUser, session: sysSession, account: sysAccount, verification: sysVerification } })` + `emailAndPassword` + `tanstackStartCookies()`。**只在服务端 import** |
| HTTP 入口 | `src/routes/api/auth/$.ts` | GET/POST 都交给 `auth.handler`(在 `(main)` 之外,所以不会被守卫拦住) |
| 登录页 | `src/routes/login.tsx` | 邮箱 + 密码;`?redirect=` 只接受站内路径(挡开放重定向);已登录会自动跳走 |
| 守卫 | `src/routes/(main)/route.tsx` → `beforeLoad` | `createServerFn` 里 `auth.api.getSession({ headers: getRequestHeaders() })`;没有会话就 `redirect({ to: "/login", search: { redirect: location.href } })` |
| 顶栏用户菜单 | `src/components/layout/topbar.tsx` | 显示姓名 / 邮箱 + **个人资料**(`/settings/profile`)+ 退出登录;用户信息由 `beforeLoad` 返回、经 `SidebarProvider` 传到顶栏(SSR 首帧就对,不会先闪"管理员") |
| 表定义 | `src/db/data-base-schema.ts` | 四张表 `sys_user` / `sys_session` / `sys_account` / `sys_verification`(auth 是**系统内部服务**,按项目口径吃 `sys_` 前缀、不进 drizzle 迁移)。**BA 的 organization 插件已撤掉** —— 组织/部门与角色走项目自己的权限五表,见下节 |
| 回归测试 | `tests/better-auth.test.ts` | 5 个用例:注册 / 登录 / 取会话 / 错密码 / 登出;每步都回查库里真的落了什么行 |

**两条硬约束**(踩过):

- **守卫必须在服务端做,而且 `createServerFn` 的 handler 里要动态 import server-only 模块**。路由文件被 `routeTree.gen.ts` 静态引用,顶层 import `#/lib/auth` 就会顺着 `#/db` 把 mysql2/dmdb 拖进客户端包 —— 浏览器里没有 `Buffer.prototype`,整个应用直接崩(同一坑的详细记录见 `routes/(main)/demo/drizzle.tsx` 顶部)。客户端的 `authClient.useSession()` 只能用于**展示**,不能当守卫:它异步,首帧没有结论,未登录的人会先看到后台外壳。
- **不开放自注册**:`/login` 只登录,没有注册页。账号得先在库里建 —— 用 better-auth 自己的接口建最稳(密码会被正确地 scrypt 哈希):

  ```ts
  // 一次性脚本(tsx 跑):pnpm exec dotenv -e .env.local -- tsx <脚本>
  import { auth } from "#/lib/auth";
  await auth.api.signUpEmail({ body: { email: "you@example.com", password: "改成强密码", name: "你的名字" } });
  ```

  注意 `signUpEmail` 会**顺手建一个会话并落下 cookie**,脚本里记得 `db.delete(sysSession)` 清掉(`sys_user` 等四表从 `#/db/data-base-schema` 导入)。
  如果需要长期可用的建用户命令(`pnpm auth:create-user`),说一声就加 —— 本轮没做是因为没确认要。

**管理员代改密码 —— BA 没有这个接口,只能写库,但必须用它的 hasher。** `changePassword` 要**本人会话**
(邮件/旧密码往返),项目也**没启用 BA 的 admin 插件**,所以"帮别人把密码重置成 X"没有 API 可用。做法:

```ts
import { hashPassword } from "better-auth/crypto";   // ← 必须用它,自己搓哈希格式对不上、登录直接过不去
const hash = await hashPassword("新密码");            // 每个账号**单独算一次**(scrypt 自带盐,别共用同一个串)
await db
  .update(sysAccount)
  .set({ password: hash, updatedAt: new Date() })
  .where(and(eq(sysAccount.userId, id), eq(sysAccount.providerId, "credential")));
```

⚠️ **改完一定要拿 `auth.api.signInEmail` 真登一次** —— 直接写库最怕的就是"写进去了但登不上"
(实测过:用 BA 导出的 hasher 写、再用它的登录接口验,才是完整闭环)。

**运维「切换用户」(免登录换身份):`lib/auth-debug.ts` 的 BA 自定义插件端点** `POST /api/auth/debug/switch-user`,
顶栏入口 `components/layout/user-switcher.tsx`,权限点 `sys:user:impersonate`。
- **必须是 BA 插件端点**:换身份 = 换一个**签过名**的会话 cookie;`createServerFn` 拿不到 BA 的签名上下文,
  自己拼 cookie 值等于绑定 BA 私有格式,写 `sys_session` 行也不够。插件端点里 `ctx` 是真的。
- ⚠️ 它用 BA 的**内部适配器** `internalAdapter.createSession`(官方 admin 插件同款)。**升级 BA 后必须重跑
  `tests/impersonate.test.ts`** —— 它真的切一次再看会话是谁,`typecheck` 抓不到这类变化。
- 服务端**必须**再查一遍权限(全站第一处真正的服务端拦截);`perms === null` 时**也拒绝**。切换不删原会话,
  身份 1 小时过期,前端记"从谁来的"并常驻徽章提示(忘了切回来是这类功能最常见的翻车方式)。
- 原身写在**签名 cookie** `impersonator_id` 里。⚠️ **连续切换时它必须保持"最初的原身"不变**
  (`impersonator ?? user.id`):否则中间那个身份会被记成原身,`队员→队长→队员→队长` 这种来回切最后一步会 403 卡住
  (原身份的授权丢了)。`tests/impersonate.test.ts` 的 A→B→C→B→C 用例盯着这条。

### 邮件:验证邮箱 / 改邮箱(SMTP,开发态走终端)

**模板不替你挑邮件服务商**,但给了**一条能直接用的路** —— `src/lib/mailer.ts` 两个驱动:

| `MAIL_DRIVER` | 行为 | 什么时候用 |
| --- | --- | --- |
| 留空(= `console`) | 把「收件人 / 主题 / 链接」打到服务端日志(`logger.warn("mail.dev", …)` + 三行 `[mail] …`),**不真发** | 本地开发:从终端把验证链接复制到浏览器 |
| `smtp` | Nodemailer 真发 | 开发联调 + **生产(必须换掉,否则用户永远收不到验证信)** |

配 SMTP 的一组变量:`SMTP_HOST` / `SMTP_PORT`(默认 587)/ `SMTP_SECURE`(留空按端口判断,465 ⇒ 隐式 TLS)/
`SMTP_USER` + `SMTP_PASS`(成对填;内网 relay 不鉴权就两个都留空)/ `SMTP_ALLOW_SELF_SIGNED`(= 1 才放行自签证书)/
`MAIL_FROM`(收件人看到的发件人,可带显示名)。

**为什么是 SMTP 而不是再挑一家 HTTP 邮件服务**:企业邮 / 阿里邮箱 / Exchange / 自建 Postfix **都有 SMTP**,
而它们大多不开或不便开 HTTP API —— 一条 SMTP 覆盖全部场景,不用为了发一封验证信去申请开发者资质。
再加别的服务商(Resend / SES / 邮件推送)仍然**只改 `lib/mailer.ts`**,调用方不碰。

实现上有三个刻意为之的地方(细节见该文件注释):

- **`nodemailer` 是动态 `import()` 的** —— 它只在真发信时才用得上,不该被 `lib/auth.ts` 的启动路径拖进来;
- **transport 复用**(它自带连接池),但**建失败要把缓存清掉** —— 否则第一次的配置事故会把 rejected promise
  钉死,补好环境变量再发信还是同一个错,像是"改了没用";
- **失败只记 `mail.smtp_failed` 然后继续抛** —— BA 的验证流程靠"邮件已发出"这个事实,吞掉就等于让人
  永远等一封不会来的信。

| 能力 | 配置 | 入口 |
| --- | --- | --- |
| 验证邮箱 | `auth.ts` 的 `emailVerification.sendVerificationEmail`(链接 1 小时过期) | 个人资料页「邮箱验证与换邮箱」卡 → BA 的 `sendVerificationEmail` |
| 换邮箱 | `auth.ts` 的 `user.changeEmail.enabled = true` + `sendChangeEmailConfirmation`(BA 默认**关**这个端点) | 同一张卡 → BA 的 `changeEmail`,确认信发给**新**邮箱 |
| 改密码 | BA 自带的 `changePassword`(要旧密码) | 个人资料页「修改密码」卡,`revokeOtherSessions: true` |
| 改姓名 | BA 的 `updateUser` | 个人资料页「修改姓名」卡,成功后 `router.invalidate()` 让顶栏名字跟着变 |

⚠️ **刻意不开 `emailAndPassword.requireEmailVerification`**:默认驱动不发真邮件,一开谁都登不进来。
生产切到 `smtp` 且确认能收到信之后再开。
页面与数据源:`src/components/modules/settings/settings-profile-page.tsx` + `trpc.user.profile`
(**只读 `ctx.user.id` 自己那一行**,所以不挂菜单授权,见 `doc/rbac-权限模型.md` 的读接口分类)。

### 登录风控:失败计数 + 锁定(`sys_account_lockout`)

模板基线:**5 次失败 → 锁定 15 分钟**(可在 `src/lib/auth-lockout.ts` 顶上调常量;测试用 `setLockoutConfig({ threshold: 2 })` 加速)。

| 设计点 | 备注 |
| --- | --- |
| 表 | `sys_account_lockout (email pk, failed_attempts int, locked_until timestamp, last_failed_at timestamp, last_failed_ip varchar(64))` —— **没有 `created_at`**,按 email 前缀扫;DDL 在两份建表脚本里都有。 |
| 滑动窗口 | `recordSignInFailure` 先把"5 分钟外的旧失败"清零再加 1,防"隔 10 分钟失败一次永远锁不上"。 |
| 触发点 | better-auth `hooks.after createAuthMiddleware` —— 拿 `ctx.context.returned.user?.id` 区分成功 / 失败;**失败的 `email` + IP 入表**;**成功的清零**。 |
| 拦截点 | better-auth `hooks.before` —— 进来先查 `isAccountLocked(email)`,锁了就抛 `APIError("TOO_MANY_REQUESTS")`。**即使用户密码输对**,也拦。 |
| 速率限制 | better-auth 的 `rateLimit.customRules`(`/sign-in/email`:60 秒 5 次,……)—— 是 IP 维度的限流,与账号锁定**互补**:5 次/分钟/IP + 5 次累计/账号。**计数落在 `sys_rate_limit` 表**(`auth.ts` 的 `secondaryStorage: rateLimitStorage`),不再放内存 —— 见下条。 |
| 测试 | `tests/auth-lockout.test.ts` 6 个用例(阈值触发、清零、手动解、after 接通、before 拦正确密码、当前锁定列表)+ `tests/rate-limit-storage.test.ts` 8 个用例(计数单调递增、跨窗口重置、KV 互通、`getAndDelete`、前缀 `list`、失败关闭、`purgeExpiredRateLimits`、`purgeExpiredRateLimitsThrottled`) —— 都走真实 BA + 真实 DB。 |
| 派生 | 无需为多副本改配置:计数已经在库里。`sys_rate_limit` 的过期行由 `purgeExpiredRateLimitsThrottled()` 清(**挂在认证请求上当心跳**,一小时最多真跑一次 —— 模板没有内置调度器)。**`storeSessionInDatabase: true` 不能删** —— BA 检测到 `secondaryStorage` 后会默认去掉 session 表(`@better-auth/core` 的 `get-tables.mjs`),删了它就没有 `sys_session` 行、也没有"在线会话"可查。锁定范围可用 `extraOrigins` / IP 白名单覆盖。 |

### 权限模型(部门 / 角色 / 菜单可见性)

**"部门当组织用",但走的不是 Better Auth 的 organization 插件** —— 那套是"选中一个当前组织 + 租户隔离",
而这里要的是"**同时属于多个部门 + 角色给权限**",语义不同(而且它会往 session 上加一个用不上的
`active_organization_id`)。所以是项目自己的四张表(管组织 / 角色 / 功能权限,见 `doc/rbac-权限模型.md`):

```
sys_dept(树)                         上海公司 / 武汉公司(可嵌套)—— 纯组织架构
sys_role(全局定义)                          管理员 / 员工 / 开发 …   ← 不随部门数增长
sys_user_dept(user_id, department_id)  张三 ∈ 上海公司、武汉公司(**不带角色**)
sys_casbin_rule:g(user, role)                      张三 → 管理员、普通员工(**权限 = 这些角色的并集**)
sys_casbin_rule:p(role, menu)                      角色能看见哪些菜单 / 能用哪些按钮
```

**权限标识 = `域:资源:动作`(三段小写),每段可整段写 `*` 通配。** 例:`sys:role:add` / `sys:role:*` / `sys:*:*` / `*:*:*`(全部权限,**含以后新增的菜单**)。
- **通配在装载时展开**(唯一实现处 `lib/casbin.ts`):把模式命中的菜单行当成"被授权"再走同一套祖先补全 —— 所以
  `use-perms.ts` 与各页面**一行都不用改**,`*:*:*` 也自动覆盖未来新增的域/菜单(不用回来补勾);想收窄再加一条模式行。
- **域 = 一级模块 key**,允许长新域;受控的是**形状不是取值** —— 菜单接口的 `perm` 用 `PERM_FORMAT` 挡住

# 数据库陷阱(MySQL 与达梦)

这两条**又长又窄**:平时用不到,一旦踩到又极难查。原先写在 `AGENTS.md` 的「已知陷阱」里,
为了让 AGENTS 保持在体积预算内(实测 `wc -c AGENTS.md` = 7602,约 7.4KB),正文挪到这里,AGENTS 只留一行指针。

---

- **MySQL 改列注释 = 重写整条列定义,漏一个子句就静默改坏列**(真实踩过):MySQL 没有 `comment on`,只能 `alter table … modify column …`,而它要求把列定义**完整重写**。踩过的两个坑:
  ① 漏了 `EXTRA` → 设置表的 `update_time datetime(3) not null default current_timestamp(3) on update current_timestamp(3)` 被改成没有 `on update`、**精度也没了**,更新数据时时间不再自动刷新,而且只有对着 `show create table` 才看得出来(`scripts/sync-table-meta.ts` 的 `COLUMN_REPAIRS` 就是补这个的);
  ② `select extra` **不写别名**读回来的是 `undefined` —— `information_schema` 的字段名是**大写 `EXTRA`**,别的字段我当时都起了别名,就漏了它。症状是"改注释把 `not null` / `auto_increment` / `on update` 一起抹了"。
  改这段代码后请一定跑一遍 `pnpm db:sync:meta` 两次:**第二次必须报「无需改动」**,否则就是没幂等、正在反复改坏列。

- **达梦改表名之后必须 `call sp_clear_plan_cache()`**:达梦有**全局执行计划缓存**,表被 `alter table … rename to …` 改过之后,
  缓存里按旧表名编译的计划仍然在 —— 症状是**看起来完全无关**的报错:`[-7009] Object is modified`(有时是 `[-2106] 无效的表或视图名[旧表名]`),
  而且**同一条 SQL 换个写法就能过**(实测:同一张表的参数化 DELETE 挂、去掉限定列名就通),极难往"表名"上想。
  两个建表脚本的「老库改表名」流程已经在 rename 之后自动清一次;手工改过表名的库记得自己跑一遍。
  顺带记住:`create table if not exists` 只认**新名字** —— 老库里还叫旧名的表它管不着,会当"没这张表"重开一张空的(见 `TABLE_RENAMES`)。
